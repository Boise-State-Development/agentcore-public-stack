# PlatformStack resource budget: the reduction plan

**Status:** Phase 0 shipped with this document. Phase 2 (§5) shipped in #1808. The IAM change (§4) is in progress. Phase 1 (§3) is proposed.
**Guard:** `infrastructure/test/platform-ceilings.test.ts` prints the live numbers on every run. Read the guard, not the figures here.

## 1. Where we are

Three limits decide whether the next feature fits. They are separate problems with separate fixes:

| Limit | Where it stands | Fixed by |
|---|---|---|
| CloudFormation's 500 resources per stack | 450 with every flag on; the guard fails above 497 | Phases 1 and 2 (§3, §5) |
| IAM's 6,144 characters per managed policy | app-api's fullest policy has about 231 free, less than one more grant renders to, and the Runtime role is close | narrowing the DynamoDB permissions (§4) |
| The V2 Runtime's 2,560-byte environment | guarded at synth by `RuntimeEnvironmentPayloadGuard` | already handled (§6) |

For scale, a SageMaker inference feature (model, endpoint config, endpoint, autoscaling, execution role, notification topics, a completion Lambda and an image repository) comes to about 15–20 resources. It also needs new permissions on app-api and the Runtime.

### Resource count

Every resource lives in one CloudFormation stack, and CloudFormation refuses a stack over **500** resources. The guard synthesizes the stack twice and fails above 497 with every opt-in flag on.

| Measured on `develop` (2026-10-31) | Shipped defaults | Every flag on |
|---|---|---|
| Before Phase 0 | 441 | 454 |
| After Phase 0 | 437 | 450 |

The grouped alarms in #1708 took the all-on count from 494 to 449 on 2026-10-22. Features have added 5 since then. Each opt-in feature we ship adds a few more, so the gap closes again unless something gives resources back.

#### What the 450 are

| Resource type | Count | Note |
|---|---|---|
| `AWS::SSM::Parameter` | 59 | the largest single type, and mostly reclaimable (§3) |
| `AWS::CloudWatch::Alarm` | 51 | already grouped where thresholds allow (#1708) |
| `AWS::IAM::Role` + `AWS::IAM::Policy` | 68 | one role and one default policy per compute identity, which is inherent |
| `AWS::DynamoDB::Table` | 29 | product data |
| `AWS::Lambda::Function` | 24 | |
| `AWS::Logs::LogGroup` | 23 | |
| `Custom::S3AutoDeleteObjects` | 13 | only when `retainDataOnDelete` is false (§5) |

The largest constructs are `KbMigration` (40), `Network` (22), `InferenceApi` (21) and `ConversationIndex` (19).

## 2. What we are not doing

**Retiring `KbMigration`.** Despite its name, its 40 resources run managed knowledge bases. It holds:

- the ingestion consumer, which puts every document into its managed KB
- the dispatcher and worker, which also create a new agent's managed KB on its first upload and tear KBs down
- the orphan and document reconcilers
- the KB storage, count and cost alarms

The dispatcher runs when migration **or** `MANAGED_KB_NEW_DEFAULT` is on. Both are on in dev and prod. The migration-only part is a few steps in the worker's code, which cost no resources.

What can eventually go is the **legacy** RAG pipeline (`RagIngestion` and the legacy parts of `RagData`). That needs two things first: every existing KB migrated in each environment, and managed KBs made the default for a fresh fork. That is a product change, so it gets its own release.

**Moving resources into a nested stack.** A nested stack counts as one resource in its parent, so this is the biggest lever available. It also breaks the single-stack rule in `CLAUDE.md`. Every explicitly named resource that moves (queue names, alarm names, log groups) has to be renamed, or CloudFormation collides creating the new copy before deleting the old one. Hold it in reserve for when Phases 1 and 2 are spent.

**Sharing log groups between Lambdas.** This saves up to about 15 resources, but each function's logs stop living in their own group. That is a real cost when debugging, for a saving Phase 1 makes unnecessary.

## 3. Phase 1: consolidate the SSM parameters (about −49)

### What the 59 parameters are for

| Group | Count | Read by |
|---|---|---|
| Deploy targets: Lambda function names, the ECS cluster, service and task-definition family, the SPA bucket and distribution, the Runtime id | ~20 | `scripts/build/*`, `scripts/frontend/deploy.sh` |
| Data resources: table and bucket names | ~30 | `scripts/backup-data`, `scripts/restore-data`, `backend/scripts/audit_user_duplicates.py`, load-test, smoke, seed |
| Read at runtime, or by operators | ~8 | the backend (`gateway/id`, `conversations/archive-bucket-name`), `.env.example` (`auth/cognito/*`), the nightly jobs (`frontend/url`), the deploy guide (`observability/alarm-topic-arn`) |

Most of the first two groups exist only so a script can find a name. Lambda names are generated by CDK, so the scripts cannot work them out themselves. Two JSON parameters can carry the same information.

### The change

1. **Publish two manifest parameters:**
   - `/{prefix}/deploy/targets`, for the deploy targets
   - `/{prefix}/data/resources`, for the data resources

   Each is a JSON object mapping a stable logical key (`kbMigrationWorker`, `usersTable`) to the physical name, plus a `schemaVersion`. There are two because one would not fit: a Standard parameter holds 4 KB, and together they need roughly that much at the 21-character maximum prefix. The guard asserts each manifest's rendered size at the maximum prefix, the same way it already does for IAM policies.
2. **Add one reader per language:** `scripts/lib/platform-resources.sh` (bash with `jq`) and `scripts/lib/platform_resources.py`. Each reads the manifest first and **falls back to the old per-resource parameter**. Every in-repo reader listed above switches to it in the same PR.
3. **Keep the runtime and operator parameters** from the third group as they are. They have stable names people type by hand, and the backend reads two of them on the turn path.
4. **Add an allow-list test** that fails when a new per-resource name parameter appears outside it, so this number does not grow back one feature at a time.

### Keeping it painless for forks

A fork can be hurt in two ways. It may deploy the infrastructure and the scripts at different times, or it may have scripts of its own that read our parameter paths. The rollout handles both:

| Release | Stack publishes | In-repo readers | Fork action |
|---|---|---|---|
| N | the manifests **and** the old parameters (`legacySsmParameters` defaults on, +2 resources) | manifest first, falling back to the old parameter | none. The release notes list each old path and its manifest key |
| N+1 | the manifests only. `CDK_LEGACY_SSM_PARAMETERS=true` brings the old parameters back | unchanged | a fork with its own scripts either updates them or sets the variable for one more release |
| N+2 | the manifests only. The switch and the fallbacks are deleted | manifest only | none for anyone who acted at N+1 |

- **The fallback order makes deploy order irrelevant.** New scripts read an old stack through the fallback. Old scripts read a new stack at release N because both are published.
- **`legacySsmParameters` is a rollout switch** under the `CLAUDE.md` rules. Its retirement condition goes in its docstring and the docs-site row, and it gets a line on the tracking issue (#1422). The CHANGELOG gets a `Deprecated` entry at N and a `Removed` entry at N+2 naming every path.
- **Docs:** the docs-site upgrade page gets the old-path → manifest-key table and a one-line `jq` recipe. `local-development.md` already says to pull values with `get-parameters-by-path`, which finds the manifests unchanged; the `.env.example` comments that name a path are updated.

**Net:** about 51 parameters become 2 at N+1, which takes the all-on count from 450 to about **401**.

**The catch is timing.** Release N adds 2 resources, and the saving lands one release later. That is why Phase 1 is not the first thing to ship before a feature that is already waiting (§7). It is worth starting early anyway, because each of its steps waits for a release.

## 4. IAM: grant DynamoDB by prefix, not table by table

**The problem.** CDK packs each role's permissions into overflow managed policies of up to 6,144 characters each. Measured on `develop` on 2026-10-31 from the every-flag-on synth:

| Role | Statements | DynamoDB's share of the policy text | DynamoDB resource entries |
|---|---|---|---|
| app-api task role | 72 | about 47% | 58 |
| AgentCore Runtime execution role | 44 | about 30% | 38 |

That share is large because each table is granted on its own, with `grantReadWriteData` / `grantReadData`. Each grant renders the table ARN, the `/index/*` ARN and the action list again.

**The change.** All 29 tables are named `{prefix}-...` by `getResourceName`. So each role's table grants can collapse into one read-write statement on `table/{prefix}-*` and `table/{prefix}-*/index/*`. A read-only statement is added only where a role genuinely must not write a table. That frees thousands of characters per role, and probably an overflow policy or two, which are resources too.

**The security catch.** `projectPrefix` may contain hyphens (`/^[a-z][a-z0-9-]{1,20}$/`), so `dev-*` also matches the tables of a deployment prefixed `dev-foo` in the same account. The statements therefore carry a condition on the `Project` tag that `applyStandardTags` already puts on every table.

**Fork pain:** none. IAM is internal to the stack; no fork reads it.

**Net:** the next feature's permissions go into the existing policies instead of a new managed policy for each grant. The PR reports the exact characters freed per role from the guard's `[policy headroom]` lines.

## 5. Phase 2: empty buckets in the teardown script, not in the stack (−13 to −15, non-retaining deployments only)

When `retainDataOnDelete` is false, every bucket gets CDK's `autoDeleteObjects`. That is one custom resource per bucket, plus the provider Lambda and its role. It is why a `production: true` synth is exactly 15 smaller. Dev and test deployments are the shape that hits 500 first, and that includes most forks' first deployment.

The change:

- `scripts/teardown/destroy.sh` empties each stack's buckets, including every object version and delete marker, before it deletes the stack. It finds them with `list-stack-resources`, not by `{prefix}-` name, so a bucket that only shares the prefix is never touched. It empties only buckets whose deployed `DeletionPolicy` is `Delete`, so a retaining deployment keeps its objects. A late log delivery that fails the delete is emptied again and the delete retried once. `--dry-run` reports without deleting.
- `getAutoDeleteObjects` is removed, and the guard fails if a `Custom::S3AutoDeleteObjects` reappears.
- The teardown docs (docs site `deployment/environments.md` "Tearing down", both troubleshooting pages) say to use `destroy.sh` rather than a bare `cdk destroy`.

**Fork pain:** someone who tears down with a bare `cdk destroy` or the console now gets "bucket not empty" and has to empty the buckets by hand. Teardown is rare and the failure message says what to do. Even so, this is a `Changed` CHANGELOG entry, and the docs-site teardown page should be checked first so it already points at the script.

**Net (measured):** exactly 15 fewer in both columns, 434 → 419 with shipped defaults and 447 → 432 with every flag on, in the release it ships in. A `production: true` synth now has the same count. A production deployment is unchanged, because it never had these resources.

## 6. The Runtime environment needs no refactor

The V2 Runtime's environment is capped at 2,560 bytes. The pattern for staying inside it already exists (`CLAUDE.md`, `docs/specs/agentcore-runtime-v2.md` §7):

- Name any `{prefix}-{suffix}` resource with `getResourceName`.
- Add its variable to `backend/src/apis/shared/config/derived_environment.json`, which `hydrate_derived_environment()` applies at startup.
- Never add it to the Runtime's `environmentVariables`.

A CDK test pins each manifest entry to the template, and `RuntimeEnvironmentPayloadGuard` fails synth over the limit. A new feature, such as a SageMaker endpoint name, only has to follow the pattern.

## 7. Order and checks

1. **Phase 0 (shipped):** delete four parameters nothing read:
   - `admin/system-prompts-table-arn` and `admin/agent-templates-table-arn`
   - `managed-kb/service-role-arn`: the backend gets this ARN as `MANAGED_KB_SERVICE_ROLE_ARN`
   - `network/alb-url`: still a stack output

   `observability/alarm-topic-arn` has no code reader but stays, because the deploy guide's verify step reads it.
2. **IAM (§4)** and **Phase 2 (§5)**, in parallel. These are what free room for a feature already waiting: IAM headroom at no cost to forks, and about −15 resources in the configuration the guard measures, with no deprecation releases.
3. **Phase 1, release N (§3)**, as soon as those are in, so the release clock starts. Then N+1 and N+2, each one PR touching CDK, the scripts and the docs together.

Projected with every flag on: 450 after Phase 0, about 435 after Phase 2, and about 386 once Phase 1 reaches N+1. A feature of 15–20 resources fits after Phase 2 alone, because the guard's ceiling is 497.

**For a new feature:** ship it behind an opt-in flag (`CLAUDE.md` § Feature Flags), and count its resources before building. Optional pieces, such as a second notification topic or a dedicated role where an existing one would do, are worth cutting. Every resource a feature doesn't add stays available for later features.

For each PR, the guard's `[resource headroom]` line is the before-and-after number, and `list-stack-resources` on dev after the Platform deploy should match it exactly. It has matched since #1685.
