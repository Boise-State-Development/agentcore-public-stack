# Extraction validation: scoring a field set against known answers, and what "improve" can safely mean

**Status:** Proposal, 2026-11-13. Nothing built. An exploration and a recommendation, written to answer one question: is our eval harness the answer to Vandalizer's *Validate & Improve*?
**Author:** Phil Merrell (with Claude Code)
**Targets:** `develop`
**Refs:** `docs/specs/eval-harness.md` (the harness, its decisions D1–D33, and §12's phase 4), `docs/specs/structured-extraction.md` (§6.4 grammar caching, §14 and §14.1 the dev check, §15 where G4 is named as a non-goal, §16.9–§16.12 the measured capacity limits, §17.8 the ten-trial readout), `docs/specs/source-provenance-verification.md` (the four states), `docs/specs/field-set-authoring.md` (§2, which leaves "anything the optimizer owns" out, and §6 on what changes a schema), `docs/specs/release-ledger.md`, `docs/one-pagers/research-admin-content-gap.md` (G1–G11, of which this is G4).

## 0. The short answer

**Partly.** The eval harness is the right home for the *platform's* half of this and the wrong home for the *office's* half.

- **The platform's half: yes.** "Does `document_extract` still get the right answers on known documents after we change the model, the schema builder or the prompt?" is a regression question, and the harness answers regression questions. A gating `extraction` family with synthetic award documents and known field values belongs in the golden set. It would have caught the bug #2063 fixes before it shipped: a 14-field set with 12 non-enum fields was refused by Bedrock at 26 unions, and every field set run on dev until the pilot had eight fields or fewer.
- **The office's half: no.** "Is *our* award-intake field set accurate on *our* awards?" is a different question with a different owner, different documents and a different statistic. The harness is built on six decisions that each forbid it: cases are JSON in git (D3), the corpus is synthetic and public (D6), it runs as one dedicated eval user (D7), never in production (D8), it reports paired regressions against a baseline rather than accuracy (D4), and only `admin.costs` holders can read its results. Putting DRED's awards in it would break the property that lets us publish it (§19).

So the recommendation (§5) is two things that share code but not a surface:

1. an `extraction` family in the platform harness, for us;
2. a **field-set check** on the field-set editor, for the office: first with no ground truth at all (run-to-run agreement plus provenance), then with known answers the office supplies by correcting a run, then suggestions for `find` phrases tested on documents the suggestion never saw.

"Improve" stays a suggestion the author applies. Nothing tunes itself.

On Vandalizer (§1): its extraction validation is real and well built, and V1–V2 here would reach parity with it, not overtake it. Its results are never "certified": the word names a discounted score in a code comment, and the one `certified` flag is a training course. Its extraction optimizer chooses among engine settings we deliberately do not have, and never rewrites a field's definition. The one place this design goes further is the `find` phrase: proposing a rewrite and testing it on documents it was not written from.

## 1. What Vandalizer's Validate & Improve actually does

Read from the code at `ui-insight/vandalizer` (v4.15.0, GPL-3, read for the reasoning and not copied), mostly `backend/app/`. The README line is "Score and automatically tune your extractions, workflows, and knowledge bases against a test set, with certified results." What the code does is more careful than that line in some places and weaker in others.

### 1.1 Extractions (their `SearchSet`, our field set)

- **The test set** is `ExtractionTestCase` (`models/extraction_test_case.py`): a label, a snapshot of the document's text, and `expected_values: dict[str, str]`, one string per field. Cases are written three ways:
  - typed by hand;
  - "from extraction", which saves the current config's output as ground truth with no review (`extraction_validation_service.py:127-189`);
  - generated by the model over 3, 5 or 10 documents, then edited and approved by the user (`extraction_test_case_generator.py`). Its docstring names the "extract once, save as truth" bias, which the "from extraction" path reintroduces. Once saved, nothing records whether a value was typed or generated.
- **Validation** runs every case three times and scores with normalised matching, no LLM: case-insensitive, currency and punctuation stripped, numeric tolerance, about ten date formats, about thirty spellings of "not found". It reports per field: accuracy, consistency (the share of runs giving the modal value), a 95% Wilson interval, enum compliance, and an error type (missing, truncated, format difference, wrong value).
- **The score** folds these into one number: accuracy × 60 + consistency × 40 (50/30/20 when cross-field rules exist), discounted below three cases or three runs, mapped to tiers at 90, 70 and 50 (`quality_service.py`).
- **"Automatically tune"** picks among a **fixed menu of engine settings** (`extraction_tuning_service.py:25-139`):
  - each model with one-pass or two-pass;
  - thinking on or off;
  - consensus of three;
  - chunking at 8 or 5 fields when a set has more than 12;
  - three canned prompt wrappers.
- **Field definitions are never rewritten.** A field under 50% accuracy gets a sentence telling the user to rewrite its definition (`extraction_optimizer.py:1352-1360`).
- **The optimizer's statistics are well built**:
  - a hash-based third of the cases is held out from four cases up, and the holdout score is the headline;
  - smaller sets are marked `overfitting_warning`;
  - the winner must beat the current config by 2σ/√N, or the run is "tied with baseline" and Apply returns 409;
  - candidates from the judge's own model family are excluded;
  - an unreachable judge is excluded, never scored zero;
  - Apply is a user click by default, revertible, and followed by a full strict-match re-validation.
- **Two weaker edges.** With a budget set, which the wizard always sends, the trial set is an unseeded random sample of the menu. Only the judge's tokens are counted, not the extraction's (`extraction_optimizer.py:52-55`).

### 1.2 Workflows and knowledge bases

- **Workflows.** The "test set" is a list of model-written check descriptions plus snapshots of earlier runs' own output, accepted by a person. There is no human-written expected answer.
  - Validation grades the **last three historical runs**, not the test inputs (`workflow_service.py:2786-2797`).
  - The expected-output comparison matches every run against every expected output regardless of input.
  - The optimizer swaps models per step and asks a model to rewrite each prompt step. It never reads the expected output (`workflow_optimizer.py:721`).
  - Its "judge variance" compares input 1 with input 2, so it measures input spread, not judge noise.
- **Knowledge bases.** Test queries carry an expected answer and sources, entered by hand, imported from CSV, or generated and saved at once.
  - The score is 40% judge, 25% retrieval, 20% source health and 15% coverage. A KB whose answers are all wrong can still score about 60.
  - Tuning sweeps retrieval-time settings only: k, model, prompt variant, query rewrite, rerank and temperature. Chunking and embeddings are deferred (`AUTOVALIDATE_FOLLOWUPS.md` §7).
  - It has the best statistics of the three: a stored seed, a paired-bootstrap interval on the lift, and a second judge with a κ check.

### 1.3 "Certified" and "verified"

- **No result is ever certified.** "Certified score" is a code comment's name for the sample-size-discounted number. The only `certified` flag in the tree is a user's completion of the Vandal Workflow Architect training course (`models/certification.py`).
- **The real mechanism is verification**: an examiner or admin approves a catalog submission, which sets `verified=True` and freezes the validation snapshot as `official_baseline` (`verification_service.py`).
  - The submission's quality gates (0.7 accuracy, 0.8 consistency) are **off by default** (`require_validation: False`), and a user can skip validation.
  - Editing a verified item raises a "config changed" alert and keeps `verified=True`.
  - An optimizer apply, a KB edit or a model change raises nothing.

### 1.4 Where it runs

- **Celery tasks:** a daily quality monitor re-validates after seven days and flags regressions against the official baseline, plus a monthly KB re-check.
- **On every run:** a validation runs after **every** extraction run that has test cases (`routers/extractions.py:1188-1190`), and after every workflow run.
- **Shadow optimizer runs** of about 200k tokens start on their own after a poor validation, a regression or KB thumbs-downs.
- **Cost controls:** three concurrent runs per user and one per item. No dollar cap.
- **Access:** any user can do all of it on items they manage. It is not an admin feature.

### 1.5 What we take from it, and what we do not

| From Vandalizer | Here |
|---|---|
| Per-field accuracy, consistency and a Wilson interval over k=3 runs | Adopted as V1–V2. **This is parity, not an advantage** |
| Generate-then-approve ground truth, and its named bias | Adopted as labelling by correction, with each cell ticked against its passage. No "save the output as truth" path |
| Holdout third, "tied with baseline" blocks Apply, judge-family exclusion, judge outage ≠ zero | Adopted for V3 |
| Tuning a menu of engine settings | **Not available to us, by design.** The extraction model is one per deployment, the call is one constrained pass, and chunking a set is the schema split §16.9 leaves unbuilt. Our tunable surface is the `find` phrase, which they do not tune |
| One blended 0–100 score and a tier | Rejected. Per-field numbers with `n` and intervals, never pooled (the harness's D4 and the ledger's D6) |
| `verified` that survives edits | Rejected. Our stamp is pinned to `field_set_fingerprint`, so an edit makes it stale by construction |
| Validate after every run, daily re-validation, self-starting shadow runs | Not in V1–V3. Each multiplies spend with no one asking. V4 re-validates only when the model or build changes |
| Extraction tokens unmetered | Ours are `C#` rows on the owner's quota |
| Per-value provenance | They have it too (it is where G2 was ported from), but their validation does not use it. Ours reports it beside accuracy, so a supported-but-wrong field (§2.3) is visible as exactly that |

**No optimizer is specified anywhere in the repo.** G4 appears as a named non-goal in `structured-extraction.md` §3 and §15 ("their `extraction_config`, `tuning_result` and optimizer… would share a runner with the unattended path") and in `field-set-authoring.md` §2. ### 2.3 Provenance is not correctness, and the pilot shows where

Provenance answers "is this value in the document", which is necessary and not sufficient. Two gaps matter for validation, and the DRED pilot's 14-field `award-intake` set (git-ignored drafts, fictional sample awards) has both:

- **Supported but wrong.** An award states several values that each look like an answer: a budget period's dates beside the project period's, the amount obligated by this action beside the total award, the original end date beside an amendment's extension. A value read from the wrong one is in the document, so it reads `supported`. The pilot's `find` phrases exist to steer between these ("the whole period of performance… not of a single budget period"), which means those are exactly the fields that fail quietly. Only a known answer catches them.
- **Never confirmable.** `award_type` and `cost_share` are enums, so they read `unassessed` / `enum_field`; `reporting_requirements` is a list, `unassessed` / `non_scalar` (§14.1 of extraction). Three of the fourteen fields can never earn `supported` on any document. A field set can be all-green on provenance and wrong on the three fields provenance cannot see.

What provenance *does* give for free is the converse: a non-optional field that reads `unverified` on most documents, or a `quote_unsupported` rate above zero, is a defect that needs no labelling to find.

### 2.4 Two more free signals

- **Run-to-run agreement.** `_build_model` sets no temperature, so the extraction runs at Bedrock's default and two runs on one document can differ. A field whose value flips between three runs on the same document is unreliable whatever the right answer is. This also costs no labelling.
- **Capacity.** `SchemaTooComplexError` names a set Bedrock will not compile. Today an author finds that out on the first real run.

## 3. What "improve" can change, and what each change costs

| Knob | Can it be tuned automatically? | Grammar recompile? | Prefix rewrite on any turn? | Verdict |
|---|---|---|---|---|
| `find` phrase | Yes: it is the field's prompt, and extraction §3 calls it "what gets tuned when a field under-performs" | **No.** `find` reaches the schema only as a property `description`, and AWS documents that a name or description change does not invalidate a cached grammar (§16.9: 14 fields compile as fast with sentence-long phrases as with three-word ones). It does change our in-process class cache key and the prompt text | No. The agent-facing `document_extract` spec is one constant per deployment; the field schema travels only on the extraction request | **The one knob worth automating, as a suggestion** |
| `optional` | A suggestion ("expected is blank on 9 of 20 documents") | Yes: it changes the schema | No | Suggest, never apply |
| `type` | A suggestion (a `string` whose expected values are all dates) | Yes, about 13–23 s by width, once per account per 24 h (§6.4, §16.9) | No | Suggest, never apply; a type is the author's contract with whatever reads the workbook |
| `enum` values | A suggestion (expected values outside the declared set) | Yes | No | Suggest, never apply |
| Splitting a set over 14 fields | A suggestion naming the split | Yes | No | Suggest; the limit is Bedrock's (§16.9, §16.9a) |
| `version` | Not a knob | No: the version appears in the prompt text (`Field set: … (version N)`) and our cache key, not in the schema | No | The author bumps it, as today (§6 of authoring: a no-op save never bumps it) |
| Extraction model | No, not per field set. `DOCUMENT_EXTRACT_MODEL_ID` is one value per deployment, and changing it is a deployment decision priced against every office | Yes, every schema | No | A comparison an admin can run, reported, never applied |
| Temperature | Not today: nothing sets one | No | No | Pinning it is a production change with its own measured PR (open question 6) |
| `SKILL.md` / Agent instructions (the reduce step) | No. Field-level ground truth does not score the cross-document judgement; §17.8 needed planted collisions and its own scorer | No | **Yes** for a project harness or Agent: instructions are in the cacheable prefix | Out of scope; eval-harness phase 4 |

The safe shape follows from the table: **automate the proposal of `find` phrases, test each proposal on documents it was not written from, show the before and after per field, and let the author save it through the editor they already have.** Everything else is a sentence of advice.

Two guards make even that honest:

- **A held-out split.** A rewrite proposed from a failing document is scored on documents the proposer never saw. With a test set of 20, that is about 14 to propose from and 6 to report on, and the report says so. Vandalizer holds out a third from four cases up (§1.1); a field-set check holds out a third from nine documents up and otherwise reports "too few documents to test a suggestion".
- **The interval, not the percentage.** Six held-out documents cannot show 95% accuracy. A field at 6/6 has a 95% Wilson interval of 61–100%. The report prints that, as `structured-extraction.md` §17.8 does, rather than a bare "100%".

## 4. Options

**A. Put office cases in the eval harness.** Reject. It inverts D3, D6, D7, D8 and D4 (§2.1), and its corpus stops being publishable the day a real award enters it. It also measures the wrong thing for an office: a paired regression against a baseline says "worse than last time", while an office needs "how often is this field right".

**B. Build eval-harness phase 4 first, and treat field sets as one kind of test set.** Not yet. Phase 4 runs whole turns against an Agent, which is the right unit for "does my Agent follow its process", and the wrong one for "is this field right": a turn adds the chat model's cost and variance on top of the extraction call, which is pure and can be called directly (§2.2). Phase 4 also has no design past one paragraph. The test-set substrate here (owner-scoped documents, expected values, results pinned to a digest) is what phase 4 would need too, so building it for field sets first does not block phase 4; it is phase 4's first case.

**C. A field-set check on the field-set editor, reusing the harness's pieces.** Recommend. It runs `extract_fields` and `verify_claims` directly, scores per field, and lives where the office already edits the set. It is also the only option that puts a number next to the thing the number is about.

**D. Rely on provenance and stop.** Reject. §2.3: three of the pilot's fourteen fields can never be confirmed by provenance, and the costliest error (a real value read from the wrong place) reads `supported`.

**And separately, for us: A′, an `extraction` family in the platform harness.** Recommend, and do it first. It is cheap, it needs no product surface, and it guards the code every office's field set runs on.

## 5. Recommendation and phased build

Each phase is useful alone, and each stops if the one before it shows no demand.

### V0 — the `extraction` eval family (platform; no product surface)

- Synthetic fixtures from `backend/scripts/eval_fixtures/`: a notice of award, an amendment that extends the period and adds funds, a solicitation, a cooperative agreement. Every value is planted, with its distractors (budget period beside project period, obligated beside total, original end beside extended end).
- A seeded skill for the eval user carrying a **14-field** set, so the family always runs at the measured ceiling (§16.9). Another set sits at the 16-union budget (§16.9a).
- One new check, `expect.extraction: {field: value | null}`, compared by type (date equality, numeric equality for `number` and `currency`, exact enum, normalised string, item recall for lists). It reads the `document_extraction` frames, which `run_agent_headless` would collect into `RunResult` the way it collects `client_tool_call` frames. Provenance states are recorded but not gated: the state is the extractor's own verdict, not ours.
- At least 10 cases, so it gates (D18). D19 allows it: `DOCUMENT_EXTRACT_ENABLED` is on in dev.
- It also publishes through §19, which gives a public, checkable "per-field accuracy on synthetic award documents" per model. That is our honest answer to "certified results" at platform level: rerunnable, failures included, and no claim about any one office's documents.
- Commit the §17.8 trial script beside it, so the reduce measurement can be rerun on a model change rather than remembered.

### V1 — "Check this field set" (no ground truth)

Behind `EXTRACTION_VALIDATION_ENABLED` (app-api only) and `features.extractionValidation`, both in development and off by default.

- On the field-set editor: **Check on documents**. The author picks up to 10 of their documents.
- The run extracts each one three times, then reports per field:
  - agreement across the three runs;
  - the provenance distribution;
  - non-optional fields that are `unverified` on most documents;
  - `quote_unsupported` above zero;
  - fields provenance cannot confirm, named as such ("enum: needs a known answer to check").
- A capacity failure is reported on the first call, before any fan-out (`extract_over_documents` already stops there).
- The run is estimated before it spends ("30 extraction calls, about $0.40 of your quota") and refuses without confirmation, as the harness's D9 does.
- It needs no labels, so it is useful to DRED on day one, and it shows whether anyone uses a check before we build a labelling grid.

### V2 — "Validate against known answers"

- **Labelling by correction.** The office runs V1 and corrects each cell to the right value or "not stated". The corrected grid becomes the test set. This is far cheaper than typing 14 × 20 values from scratch. The risk is anchoring, because a reviewer tends to accept what is shown, so each cell must be ticked "checked" against the document passage before the set counts (open question 3).
- **Scoring.** Typed comparators per field, a new pure module (`apis/shared/extraction/grading.py`). It must not import `source_provenance` privates; the architecture test forbids that. List fields are scored by item recall with the `grounded`-style judge as advisory, as the harness does for prose.
- **The result.** Per-field accuracy with `n` and a 95% Wilson interval, the provenance distribution beside it, and a confusion line for each failing field ("read the budget period end on 4 of 20").
- **The stamp.** The result is pinned to `(field_set_fingerprint, extraction model id, Runtime build, test-set digest)`, and the field-set card shows "Checked 2026-11-20 on 20 documents" until any of those changes. Then it reads "Not checked since this set changed". It is a dated measurement, never a pass/fail badge and never the word "certified".

### V3 — "Suggest better `find` phrases"

- For a field under the author's threshold, a proposer model sees the field's definition, the expected values and the passages behind the failures (from the provenance locators). It proposes up to three rewrites.
- Each rewrite is scored on the proposing split and reported on the held-out split. A rewrite that does not beat the current phrase on the held-out split by more than run-to-run noise is shown as "no better than what you have", and is not offered to save (Vandalizer's tie rule, §1.1). Otherwise the author sees before and after per field and saves one through the editor. The fingerprint changes, so the V2 stamp goes stale and invites a re-run.
- Because only descriptions change, no candidate pays a grammar compile (§3).
- Suggestions for `optional`, `type`, `enum` and splitting are text, never edits.
- An admin-only **model comparison** reruns a test set on another catalog model and reports it. Reruns go through `grants_model_access`, and an uncatalogued id is refused.

### V4 — only on a signal

- **Re-validation on change.** A validated set reruns when the deployment's extraction model or build changes. The ledger already knows both. This is Vandalizer-style drift detection, and the point where an EventBridge schedule or the unattended queue of extraction §15 becomes justified.
- **Agent test sets.** Eval-harness phase 4, on the same owner-scoped test-set rows.

### Where it runs

- In **app-api**, never inference-api, whose only reachable paths are `/invocations` and `/ping` (CLAUDE.md, "Inference API boundary").
- V1–V3 run as a background task with a run row, resumable by skipping documents already scored, the way the harness's D9 resumes.
- A 20-document × k=3 run at concurrency 4 and the measured ~3 s warm call (§16.11) takes about one to two minutes, plus up to ~23 s for a cold grammar.
- An app-api task can die mid-run, so the run must resume, and V1–V3 stay attended. A run that must survive a deploy is extraction §15's unattended path, and its trigger condition still stands.
- App-api needs `DOCUMENT_EXTRACT_MODEL_ID`, which today is written only to the Runtime while extraction is on. App-api's environment has no 2,560-byte budget, so this is one more variable.

### Where the data lives

- **Documents.** A validation set needs documents that outlive a conversation. The cheapest path is a hidden owner-scoped session (`valset-<id>`), so presign, preparation, `session_documents` and the attachments KB all apply unchanged. It must be filtered out of the sidebar and conversation search (open question 1).
- **Expected values and results.** `VALSET#` and `VALRUN#` rows in sessions-metadata on the existing `SessionLookupIndex` GSI, the `TSUM#` / `EXTR#` pattern. No new table or index.
- **Content.** Expected values are the office's data in the office's rows, the same class as the `EXTR#` rows extraction already writes. Nothing reaches EMF or the ledger except counts: no field name, value or field-set name (extraction §14).

## 6. Cost, against the tenets

**TTFT.** Nothing here runs on the turn path. Every phase is app-api or the eval CLI. V0 adds one frame type to what `run_agent_headless` collects, and the runner is not the turn path.

**Prompt cache.**
- No validation call shares a prefix with any turn. The extraction request has no conversation, and its schema is not in any turn's `toolConfig` (extraction §5).
- Applying a V3 suggestion changes a field set's description text only, so it rewrites no turn's cached prefix. The extraction request's grammar stays cached, because descriptions do not invalidate it.
- A `type`, `enum` or `optional` change costs one grammar compile (13–23 s, once per account per 24 h). It rewrites no turn's prefix.
- One opportunity, not built: k repeats of one document could read the document from cache if the request put the document ahead of the field list and marked a `cachePoint`. Today the field list comes first. Reordering changes the production prompt and needs its own measurement.

**Model spend.** The basis is the measured extraction call in extraction §14.1: $0.0050 for 2,896 input and 338 output tokens on `us.` Haiku 4.5, which is $1.10 and $5.50 per million. An award package of about 15 pages of text is roughly 10k input and 400 output tokens, so about **$0.013 a document**. That is an estimate until V1's first run measures it.

| Phase | One run | Who pays |

## 8. Open questions for the developer

1. **Where do a validation set's documents live?** A hidden `valset-` session reuses the whole upload path. Is a hidden session acceptable, or should test documents be a project's Files?
2. **Do test sets travel with a shared skill?** The recommendation is no: they are the owner's evidence and may name real awards. A shared field set would then show the owner's dated stamp without the answers. Is that the right disclosure?
3. **Is labelling by correction acceptable for DRED**, given anchoring? The alternative is blind entry on a sample.
4. **A threshold, or only numbers?** The recommendation is a dated measurement with intervals and no pass/fail badge, because any threshold we pick is a policy for the office's risk, not ours.
5. **Is validation DRED's priority, or automations?** Vandalizer's other gap (run on upload or schedule, G6) may matter more to an office processing awards weekly. V1 is small enough to put in front of DRED and learn which one they reach for.
6. **Should production extraction pin a temperature?** V1's agreement figure measures today's default. Pinning one would raise agreement, change what every office gets, and needs a dev readout first.
7. **Per-field-set extraction model?** Today it is one per deployment. If V3's admin comparison shows a field set that needs a stronger model, the next step is a frontmatter key checked by `grants_model_access`. Do we want that door?
8. **Does V0 go first regardless?** It is independent of DRED and would have caught the union-budget bug #2063 fixes. The recommendation is yes.
