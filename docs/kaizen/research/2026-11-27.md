### What's moving this week

This is a holiday week. Vendors shipped almost nothing for agent builders. Anthropic posted only its IPO close, OpenAI posted research, and AWS shipped Web Search languages, a `STREAM` mode for Gateway response interceptors, the Trusted Access API preview and a WAF rule group for AI endpoints. The AgentCore SDK shipped an `@app.warmup` decorator that matches the warmup hook we built ourselves the same week.

The convergence this week is **keeping the tool list stable while the tools grow**. Strands' dynamic tool loading (stub schemas plus `load_tools`), opencode moving rarely used tools behind Code Mode (about 700 tokens a request saved, #66465) and Pydantic AI's ToolBridge all attack the same cost: a long `toolConfig` prefix for users with many MCP tools. The second pattern is **pause-in-place for delegates**. Pydantic AI's `SubAgents` now pass a delegate's deferred calls up to the parent and resume it in place (#14115), and assistant-ui tags interrupts with the `subagentRunId`. Both match our handoff relay, and both suggest tagging relayed prompts with a run step.

### Patterns worth considering

- **A constant tool list while the tools grow** — deferred tools show the model a name, a description and an open schema, and the full schema loads on demand. Strands (#5699, stub mode on `BedrockModel`), opencode (#66465, Code Mode) and Pydantic AI (ToolBridge) all shipped a version of it.
  - **Where**: harness-sdk 1.66.0, opencode 2.4.2, pydantic-ai 2.76.
  - **Fit**: our users with several MCP servers carry the longest `toolConfig` prefixes, and every MCP list change rewrites it. Adopting it costs one load round per first use and an unknown quality hit.
  - **Verdict**: Worth trying, measured first (Top 5 #4).
- **Delegates pause through the parent** — a sub-agent's approval or question surfaces in the parent and is answered in place (Pydantic AI #14115, assistant-ui #10743).
  - **Where**: pydantic-ai 2.74, assistant-ui react-ag-ui 0.1.12.
  - **Fit**: matches our handoff relay. The one gap is attribution: a relayed prompt inside a workflow run doesn't say which step is waiting.
  - **Verdict**: Monitor; fold into the workflow-runs SPA when a run step can pause.

### Repeated friction signals
- **The nightly is red, and it has two causes** (5 of the last 7 nights; no eval run published since 11-23, per PR #2498)
  - **Deploy**: `nightly-develop-PlatformStack` fails `CREATE_FAILED AWS::EC2::VPC … The maximum number of VPCs has been reached` on 11-24 through 11-27. A read-only `describe-vpcs` on dev shows six VPCs, two of them `nightly-develop-code-sandbox-vpc`, tagged with two earlier `nightly-develop-PlatformStack` stack ids. Neither stack exists now, and neither VPC has an ENI left.
    - **Hypothesis**: since PR 2245 each stack makes two VPCs (Network + code sandbox). The nightly teardown deletes the stack but leaves the sandbox VPC, probably because the VPC-mode interpreter's ENIs drained after the delete was attempted, and the leftovers fill the regional quota.
    - **Fix candidate**: delete the two orphans (ops, after confirming they're unused), then make the nightly teardown wait for the sandbox VPC's ENIs and delete it, or sweep VPCs tagged with a deleted `nightly-develop` stack id before the next create (`nightly-deploy-pipeline.yml`).
  - **Tests**: `tests/apis/shared/files/test_held_bytes.py::test_a_long_conversation_counts_in_well_under_a_millisecond` fails every run (1 failed of ~22k), asserting `per_call_ms < 1.0` under coverage on a shared runner.
    - **Hypothesis**: coverage tracing multiplies the per-call cost of a pure-Python walk. It's the same lesson as the memory-stats flakes: no wall-clock bounds in the suite.
