## TL;DR

**The most important external move is a quiet one: AgentCore Memory now keeps short-term events for up to 10 years (11-17).** Our Memory construct clamps `eventExpiryDuration` to 365 days (`memory-construct.ts:82`, `AGENTCORE_MEMORY_EVENT_EXPIRY_MAX_DAYS`). That clamp is the root of the 90-day-cliff work: the archive backfill, the two prunes and the daily pruner. One upstream limit change could retire a whole class of chores. That is the recommended **#1**. A close second is the AgentCore release notes saying the V2 Runtime environment limit is now 4 KB, the same as V1. ### 1. Lift the Memory expiry clamp to 10 years
- **Source**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-bedrock-agentcore-memory-10-year-retention/ (11-17); `memory-construct.ts:82`; `config.ts:1374-1375`; the queued [2026-10-07] archive-backfill and cliff-prune chores.
- **Surface area**: `infrastructure/lib/config.ts` (`AGENTCORE_MEMORY_EVENT_EXPIRY_MAX_DAYS`, the synth banner at `:2543`, the validation at `:3011`), `memory-construct.ts`, the CDK test for the clamp, and `docs/specs/` for conversation retention.
- **Change**: first confirm the new maximum in the `AWS::BedrockAgentCore::Memory` CloudFormation schema (`cfn-lint` or `aws cloudformation describe-type`), because the announcement doesn't name the field. Then raise `AGENTCORE_MEMORY_EVENT_EXPIRY_MAX_DAYS` to 3650. Deploy dev and read the memory's `eventExpiryDuration` back. Because expiry is read when each event is written, existing events keep their old expiry. Write down what that means for prod: the cliff for conversations older than about 90 or 365 days does not go away retroactively, so the archive backfill still matters for old events. Finally, reassess which of the queued cliff chores are still needed for new events.
- **Subtracts**: the clamp, and the class of "Memory forgot what the archive kept" incidents for every conversation written after the deploy. Possibly the daily pruner too, if retention becomes one number.
- **Unlocks**: a deployment can choose one retention period and have Memory honor it.
- **Effort × Impact**: Medium × **High**.
- **Verdict**: Worth trying. Check storage cost against `conversationRetentionDays` before raising prod.

### 2. Re-measure the V2 environment limit
- **Source**: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html (October entry: "up to 4 KB of environment variables… the same limit as V1"); `runtime-environment-payload-guard.ts:9,33` (2,560 bytes, from AWS's own 10-09 error).
- **Surface area**: the guard constant and its comment, CLAUDE.md's Key Conventions line, and `agentcore-runtime-v2.md` §7.
- **Change**: on dev, call `UpdateAgentRuntime` on a throwaway V2 runtime with a ~3.5 KB environment (the guard's estimate formula tells you what AWS will count). If it's accepted, set the constant to AWS's new number, re-date the comment, and update the two docs. Keep `derived_environment.json`: deriving names is good practice whatever the limit. Keep "written only while on" for in-development flags, because that rule serves forks too. Only the alarm tone in CLAUDE.md changes.
- **Subtracts**: about 1.5 KB of pressure that currently shapes every new Runtime flag's wiring.
- **Effort × Impact**: Low × Medium.
- **Verdict**: Worth trying. It's a one-call measurement.

### 3. Move the hosted FastMCP servers to 4.2.x

- **Unlocks**: servers can publish skills beside their tools (`skills/list`, digest-checked `read_skill`), which our agentskills.io import path could consume later.
- **Effort × Impact**: Low × Medium.
- **Verdict**: Worth trying.

### 4. An approval dies when its step changes
- **Source**: https://github.com/assistant-ui/assistant-ui/pull/10710; Pydantic AI `DeferredToolRequests.validated_args` (v2.71.0); `workflow-runs.md:367` (steps edited at the sheet) and `:593` (acceptance compares each step's card).
- **Surface area**: the workflow-runs acceptance route under `app_api/handoffs/workflow_runs.py` and `apis/shared/handoff/runs.py`, plus `handoff-review-sheet.component.ts`.
- **Change**: add a route test. Propose a run, approve it, change one step's request (or remove one) through the edit path, then accept with the original approval. The test asserts a refusal, and that nothing is written. Add the mirror SPA spec: an edit clears the sheet's approved state. If the comparison already holds, this is a guard; if it doesn't, it is a real bug found before the flag goes on.
- **Subtracts**: addition only. It's justified because workflow runs is the first surface where a user edits a proposal before approving it, and W.4b/W.4c are still open, so it's cheapest now.
- **Effort × Impact**: Low × Medium.
- **Verdict**: Worth trying, before W.4b merges.

### 5. Design note: cache-stable tool search
- **Source**: https://github.com/pydantic/pydantic-ai/releases/tag/v2.71.0 (`ToolBridge`: a fixed tool list behind `tool_search`/`tool_describe`/`tool_call` "so the prompt cache holds"); `docs/specs/tool-search-token-bloat-strategy.md`.
- **Surface area**: that spec now. Later, possibly `agents/main_agent/tools/` and the MCP tool registration path.
- **Change**: add a section to the spec comparing `ToolBridge`'s three fixed meta-tools with our options. Cover: what stays in `toolConfig` (constant per deployment), where the discovered schemas land (history, append-only), how RBAC filters `tool_search` results, and how `readOnlyHint` survives for concurrency. Measure the `toolConfig` tokens for a heavy-MCP user with `scripts/measure_tool_spec_tokens.py` to size the prize.
- **Subtracts**: if adopted, the per-user `toolConfig` that grows with every connected MCP server and rewrites the prefix when a connection changes.
- **Unlocks**: users with dozens of connectors, without paying for every schema on every call.
- **Effort × Impact**: Medium × Medium–High.
- **Verdict**: Worth trying, as a design note first.
