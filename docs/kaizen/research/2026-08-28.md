## TL;DR

**We have been quoting the wrong cache-write price, and our rate table is on the wrong pricing tier.** Following last week's own recommendation, the Bedrock rates were pulled from the **AWS Price List API** instead of the JS-heavy pricing page that had defeated three consecutive scans — and it produced a correction. Bedrock's cache-write premium is not the flat "$2.50/MTok" quoted twice in CLAUDE.md; it is a **1.25× multiplier on base input** (2× at 1h TTL, read 0.1×). Worse, our `us.anthropic.*` model ids are **Regional CRIS profiles**, which price exactly **10% above Global** — and [`curated-models.ts:135`](frontend/ai.client/src/app/admin/manage-models/models/curated-models.ts:135) carries the *Global* numbers under a `us.` id. The ratios are right; the base is 10% low. Recommended **#1** is the cheapest item in the scan, and it sits upstream of every other cost number we compute.

**Strands 1.53.0 also moved the prompt-cache floor under us.** PR [#3681](https://github.com/strands-agents/sdk-python/pull/3681) is marked breaking: `CacheConfig(strategy="auto")` — which we set at [`model_config.py:389`](backend/src/agents/main_agent/core/model_config.py:389) — now places a **system-prompt cache point automatically**, and we already hand-place one at [`agent_factory.py:213`](backend/src/agents/main_agent/core/agent_factory.py:213). The 40-line comment documenting our three-point layout asserts behavior that is no longer true. That is a trap for the next routine bump, and it is in the most cost-sensitive file we own.

And a **negative result that retires last week's #1 idea**: there is no Anthropic "change tools mid-conversation without invalidating the cache" beta. The current caching documentation states flatly that modifying tool definitions invalidates the entire cache, with no beta header, parameter, or dated availability anywhere. Last week's top recommendation rested on one announcement sentence the documentation does not support, and three other queue entries lean on it.

Internally: one **verified latent 400** (a `temperature` sent to Claude Opus 4.7+ passes straight through our param filter and hard-fails the turn), two model retirement floors inside seven weeks, and a **correction to our own kaizen process** — the nightly `DELETE_FAILED` entry we resolved on 2026-08-14 as "green 12 consecutive days" recurred on Aug 20 and cascaded on Aug 21.

## External Scan

### What's moving this week

Where the last window was thematically convergent — everyone attacking the prompt cache at once — this one is **corrective**. Three of the loudest claims from two weeks ago turned out to be softer than reported, and the sources that settled them were the primary ones we had not yet read.

The tool-mutation beta is the big one: it does not exist as a usable API surface. But the MCP Apps verifications went the other way and **vindicated code we already shipped** — the capability identifier is `io.modelcontextprotocol/ui` nested under `capabilities.extensions`, which is exactly what [`mcp_apps.py:7`](backend/src/agents/main_agent/integrations/mcp_apps.py:7) advertises, and `ui/notifications/tool-input-partial` is present in the spec text with the precise zero-or-more-then-final semantics our `ui_tool_input_partial` relay implements. The SDK overview page that omitted it was incomplete, not authoritative. On top of that, MCP explicitly specifies backward compatibility for initialization-based revisions, which downgrades the `serverInfo` break from "breaks on contact" to "migrate deliberately." Three separate red flags from last week resolved in our favor.

The genuinely new work is in **Strands**, which shipped two minors in the window and put both of them in our blast radius. Beyond the breaking auto-mode cache change, [#3858](https://github.com/strands-agents/sdk-python/pull/3858) fixed the exact `ValidationException` that we recorded as blocking the Anthropic cookbook's layered-TTL technique, and [#3999](https://github.com/strands-agents/sdk-python/pull/3999) added a first-class `cancel_signal` that reaches the in-flight Bedrock request — something our own dropped-stream fix (#863) explicitly cannot do, since it releases the lease while the model call keeps streaming and keeps billing.

The quiet theme is **cost attribution moving per-lane**. Claude Code split `promptCacheTtl` from `subagentPromptCacheTtl` and added per-agent `experimental.cacheTtl`; pydantic-ai added `Model.resolve_prompt_cache_retention()` in the same month. Two independent harnesses concluding that cache retention is a per-lane decision, not a global one, is a real signal for a codebase whose lanes (interactive chat, `@`-mention swap, scheduled/headless run) have wildly different re-read profiles.

The surprise was how much of this window's value came from **primary sources contradicting summaries**. A PyPI summarizer again mangled version data (claiming fastmcp's latest was 2.14.7 when it is 3.4.7) — the second consecutive scan with that failure. The version-pin table below was produced entirely by parsing raw registry JSON locally, at zero web budget, and should be done that way permanently.

  2. **Classify the overflow.** `grep -rn "ContextWindowOverflow" backend/src/` returns **zero hits** — we have no classification anywhere, so an overflow presents as a generic AgentCore 424 (which, per our own reference note, means only "the container returned some non-2xx"). Pattern-match the Bedrock overflow strings and raise something nameable.
- **Subtracts**: partial — replaces an unbounded path with a bounded one, and replaces an opaque 424 with a typed error. No new abstraction or dependency.
- **Prompt-cache caveat (load-bearing)**: the cap must be **deterministic on content** — length and base64 detection — never on "how full is the window right now." A cap that fires only near the limit would rewrite already-cached history bytes and convert a correctness fix into a cache-write cost bug. Their implementation is content-keyed, so it ports safely, but this is the thing to get wrong.
- **Effort × Impact**: **Medium × Medium–High.** The hole is verified; the fix is a known-good reference implementation; the risk is entirely in the cache interaction, which the existing stability tests bound.
- **Verdict**: **Worth trying** — do the cap first and the offset-reconciliation half only after reviewing it against `test_compaction_stability.py`.

### Runner-up (not in the Top 5): fix the nightly teardown, and stop resolving flakes on green streaks

- **Source**: internal — nightly runs [32352550026](https://github.com/Boise-State-Development/agentcore-public-stack/actions/runs/32352550026) (Aug 20, teardown `DELETE_FAILED` on `InferenceApiAgentCoreRuntime42085C46`, `NotStabilized` / "Request timed out while deleting") and [32466787516](https://github.com/Boise-State-Development/agentcore-public-stack/actions/runs/32466787516) (Aug 21, deploy blocked: "stack is in DELETE_FAILED state and can not be updated"), against the [2026-07-24] queue entry resolved on 2026-08-14 as green-for-12-days.
- **Surface area**: the nightly workflow's teardown and deploy steps. No application code.
- **Change**: (a) make the teardown resilient to an AgentCore Runtime delete that times out — retry, or detect a pre-existing `DELETE_FAILED` at the start of the deploy and clear the stuck runtime before deploying, so night N+1 isn't lost to night N's flake; (b) a one-line process rule for the kaizen skills: **resolve a flaky entry only on a root-cause fix or an explicit "accepted flake, N/month" note — never on a consecutive-green count.**
- **Subtracts**: yes — retires a recurring two-night CI loss and a resolution rule that produced a false negative within four days of being applied.
- **Effort × Impact**: **Low × Medium.** Small work; the value is that a flaky teardown currently costs two red nights, and that we now have a documented instance of our own process closing something prematurely.
- **Verdict**: **Worth trying.**

## Take

The most useful thing this scan produced is **two corrections to things we thought we knew**, and both came from following last week's own advice about sourcing. Using the AWS Price List API instead of scraping the pricing page — recommended in the last doc, acted on in this one — surfaced that our cache-write premium constant is wrong for every model we run and our rate table sits a tier below our model ids. Reading the caching *documentation* instead of the product announcement surfaced that last week's recommended #1 was chasing a beta that does not exist, a premise that had already propagated into four queue entries. Neither of those was a new event in the window; both were things that had been true for a while and that we had simply never checked against a primary source. That is the pattern worth naming: **this scan's highest-value output was not news, it was verification.**

Catching the tool-mutation premise costs one paragraph now and would have cost a week of probing later. The MCP verifications went the other way and were equally worth doing — both answers came back matching code we already shipped, which means two "do not write code until verified" blockers can simply be struck and a previously-resolved entry can be recorded as having been right all along.

The system is still trending **toward** the ecosystem, but the direction of travel has changed shape: where we used to be ahead on measurement and behind on escape hatches, Strands has now shipped three primitives that land directly on things we hand-rolled — a system-prompt cache point, a TTL-inheritance fix for the exact `ValidationException` we recorded as a blocker, and a cancellation signal that can stop an in-flight Bedrock call we currently keep paying for after the client is gone. That is a lot of subtraction available in one bump, which is also why the bump is not routine: #3681 is marked breaking, and the 40-line comment in `model_config.py` that explains our cachePoint layout will actively mislead the next person who bumps without reading it.

The one change Phil would notice first if shipped is not in the Top 5 — it is **Cursor's queue-instead-of-interrupt composer**. It is a better answer than the draft-recovery pattern flagged last week, because the draft is never destroyed rather than merely recovered, and it makes our 409-on-duplicate-turn unreachable for user-typed follow-ups. Angular-native, no dependency, an afternoon.

And a note on our own practice: we resolved the nightly `DELETE_FAILED` entry two weeks ago on twelve consecutive green nights, and it failed four days later with the identical root cause. A green streak is evidence a flake did not fire, not evidence it was fixed. That rule is worth writing down, because this scan is where we would otherwise learn it again.
