Internally, research verified **two small bugs in how we treat a finished model call**:

- **Side-channel summarizers.** They trust any stop reason except `max_tokens`. A guardrail stop can therefore become a compaction checkpoint in the cacheable history.
- **The Stop button.** It can write an `interrupted` marker onto a turn that already finished.

Both fixes are small and both are verified on disk.

## Friction — the week's signal

### 2. Treat any non-`end_turn` stop reason as a failed side-channel call
- **Source**: research/2026-09-25.md ▸ Top 5 #2 (Claude Code 2.1.282); review-queue.md ▸ [2026-09-25].

- **Change**: accept only `end_turn`. Any other stop reason returns `None`, so the existing fallback runs: truncation-only compaction, or the SPA's deterministic tool-summary formatter. Add one stubbed `guardrail_intervened` test per site.
- **Subtracts**: no. It is an addition, justified because a refused compaction summary becomes a checkpoint in the **cacheable history** for the rest of the session. That silently costs quality and cannot be undone until the next cut. The fallbacks already exist.
- **Effort**: Low
- **Impact**: Med
- **Evidence**: verified on disk (both predicates). The exact stop reason Bedrock returns for a refusal is unknown, and this change makes it irrelevant.
- **Ship means**: one backend PR, two predicates, two tests.
- **Decline means**: a guardrail stop on user content keeps becoming conversation history.
- **Recommendation**: **Ship.** It is the cheapest item on the board and it protects the cache contract's quality half.
