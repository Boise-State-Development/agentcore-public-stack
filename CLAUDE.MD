# CLAUDE.md

Production-ready multi-agent conversational AI system built with AWS Bedrock AgentCore and Strands Agents.

## Build & Run

### Backend
```bash
cd backend
uv sync --extra agentcore --extra dev   # All deps
uv run python -m pytest tests/ -v       # Tests
cd src/apis/app_api && uv run python main.py    # App API (port 8000)
cd src/apis/inference_api && uv run python main.py  # Inference API (port 8001)
```

### Frontend
```bash
cd frontend/ai.client
npm install
npm run start    # Dev server (port 4200)
npm test         # Tests (Vitest via Analog.js)
```

### Infrastructure
```bash
cd infrastructure
npm ci
npx tsc --noEmit
npx jest
npx cdk synth
npx cdk deploy {prefix}-PlatformStack
```

### Smoke / regression pass
```bash
cd backend && uv run python scripts/smoke_turns.py --help   # L1 turn matrix; see docs/testing/smoke-regression.md
```
The `/smoke-regression` skill runs the full pass (hermetic suites → turn matrix on dev or a local stack → in-app-browser checklist). Run it after any change to the turn path or an SSE event, and once per release.

## Key Conventions

- **Single CDK stack.** All AWS resources live in `PlatformStack`. There are no cross-stack dependencies to manage and no other CDK stack to deploy in a particular order. Application code is shipped out-of-band by `backend.yml` via AWS APIs (ECR push → ECS service update / Lambda code update / AgentCore Runtime update), not via CDK.
- **Deploy order:** `platform.yml` (CDK) when infra changes → `backend.yml` (parallel per-image: app-api, inference-api, rag-ingestion, artifact-render) → `frontend-deploy.yml` (S3 + CloudFront). Bootstrap data seeding is a one-time post-deploy step. Day-to-day backend code changes only run `backend.yml`.
- **Compute image URIs are read from SSM at CFN deploy time** (`/<prefix>/app-api/image-tag`, `/<prefix>/inference-api/image-tag`). The build pipeline owns those parameters; CFN always picks up the latest live image when re-registering the task def or Runtime, so infra-only deploys never revert a live service to the bootstrap stub.
- **The AgentCore Runtime's environment is a 2,560-byte budget on V2, so resource names are derived, not sent.** Any variable that is `{prefix}-{suffix}` (tables, buckets, the vector index, the workload identity) belongs in `backend/src/apis/shared/config/derived_environment.json`, which `hydrate_derived_environment()` applies first thing in `inference_api/main.py`; a CDK test pins each entry to the synthesized template, and `RuntimeEnvironmentPayloadGuard` fails synth for a V2 runtime over the limit. Don't add such a name to the Runtime's `environmentVariables`; add it to the manifest and have CDK name the resource with `getResourceName`. See `docs/specs/agentcore-runtime-v2.md` §7
- **Admin endpoints** go under `/admin/<domain>/`, user-facing under `/<domain>/`
- **Errors stream as assistant messages** via SSE (not HTTP error codes)
- **Signal-based state** throughout frontend (`signal()`, `computed()`)
- **Prompt-cache stability is a contract.** Bedrock prompt caching is exact-prefix-match: any list that reaches the system prompt or `toolConfig` (skills, tools, models, MCP tool listings) must be deterministically ordered at its source, and restored conversation history must be byte-stable between compaction-state changes (see the truncation anchor in `TurnBasedSessionManager`). An order flip or history mutation between turns silently re-writes a 30k–150k-token prefix at the cache-write premium, which is **1.25× the model's own base input rate** (2× at 1h TTL; a cache read is 0.1×) — there is no flat per-MTok figure, so price it against the model actually in play: $1.375/MTok on our default Haiku 4.5, $4.125 on Sonnet 4.6. Our `us.*` ids are **Regional (CRIS)** inference profiles and price ~10% above `global.*` for the same model; rates live in `curated-models.ts`. Per-model AWS **model cards** stay the primary source — they carry context windows, caching support, parameter tables and cutoffs, which no pricing API does — but the **Price List API now corroborates almost all of them**, and a rate worth trusting should agree in both. **Which offer file matters more than which vendor:** `--service-code AmazonBedrockFoundationModels` (372 us-west-2 SKUs) carries Claude, Cohere, Palmyra, TwelveLabs, Luma, Stability; `--service-code AmazonBedrock` (1052) carries Nova, xAI, Google, DeepSeek, Qwen and Moonshot. Querying the wrong one returns nothing and reads exactly like an unpublished model — which is how an earlier revision of this note concluded the API held "10 Claude SKUs, none newer than Claude 3." **That is no longer true** (re-verified 2026-09-21): every Claude model we curate is present and matches its card to the cent — Haiku 4.5 $1.10/$5.50 Regional and $1.00/$5.00 Global, Sonnet 4.6 $3.30/$16.50, Opus 4.7 $5.50/$27.50, Sonnet 5 $2.00/$10.00 Global, Fable 5.1 $10/$50 Global with a cache read of $0.25 that independently confirms its 0.025× multiplier. The 1.100× Regional premium reproduces throughout. **Two traps remain.** The `model` attribute is gone from the product schema — match on `servicename` (FoundationModels) or `usagetype` (AmazonBedrock), or every filter silently returns zero. And the hosted OpenAI family (`us.openai.gpt-5.6-*`, `us.openai.gpt-6-astra`, `openai.gpt-5.4`) is genuinely absent from **both** offer files, so its cards remain the only source; the old explanation that Marketplace billing is uncovered is wrong — Claude's rows are `MP:` usagetypes and are covered. `PROMPT_CACHE_OBSERVABILITY_ENABLED=false` disables the observability layer (fingerprint hook, cacheStatus derivation, EMF metrics) — the caching itself stays on
- **Token cost effectiveness is a design tenet — engineer against waste, not against context.** Before merging a change that touches the model call path, answer: what does this add to the prompt, on every turn, for the life of every session? (1) Anything in the cacheable prefix (system prompt, `toolConfig`, restored history) must be deterministic and append-only — see the prompt-cache contract above. (2) Per-turn payloads (tool results, MCP responses, retrieved documents) should be bounded or offloaded, never unbounded pass-through. (3) Don't guess — verify: `cacheStatus` + fingerprint hashes on the session's `C#` rows, `GET /admin/costs/sessions/{id}/calls`, and the `AgentCoreStack/PromptCache` EMF metrics exist to prove a change's cost impact. The balance: "cost effective" means eliminating waste (avoidable cache re-writes, duplicated context, oversized payloads) — it never means stripping context the model needs for a quality answer. When cost and answer quality genuinely conflict, quality wins; look for the cheaper path to the *same* quality, not a cheaper answer
- **Verify a release against the ledger, not a smoke run.** A smoke run is a dozen turns on one build; the release ledger (`docs/specs/release-ledger.md`) is every turn on every build, with generated caveats that say when it cannot tell. `backend/scripts/release_readout.py` (the `/release-readout` skill) writes the candidate-vs-baseline readout, caveats first, and the skill ends in ship, watch or investigate; the `cutting-a-release` skill puts the outgoing release's readout in the release PR. Read the mix shift before any delta, and treat a value under its floor (`—`) as no evidence, never as zero
- **The turn path is mapped, stage by stage, in `docs/specs/turn-path-ttft.md`** — every stage from the SPA's send to the first token, with what runs where, what is network, what blocks the event loop, and which `turn_prelude` mark times it. Read it before touching `inference_api/chat/routes.py`, `chat/service.py`, `base_agent.py`, `session_factory.py` or the stream coordinator; the route's phases (`_resolve_turn_attachments`, `_prepare_session_state`, `_check_turn_quota`, `resolve_turn_agent`, `compose_turn_system_prompt`, `apply_turn_prompt_extras`, `_resolve_turn_model`, `_resolve_effective_tools`, `_build_turn_tools`) are named for that map. A handoff brief must build the agent a turn would, so it calls these same phases, never a copy. It also carries the regression plan for this path (§6): the invariants, the tests per change, and the dev recipes that settle a timing claim
- **Time to first token (TTFT) is a hard budget — add no latency before the first token.** That path is everything between a request arriving and the first streamed token: request handling in `inference_api/chat/routes.py`, agent build/cache lookup, MCP pre-flight, and every `BeforeInvocationEvent` / `BeforeModelCallEvent` hook — the latter fires before *every* model call, so its cost repeats on each tool round. Default pattern: a hook captures raw facts only, and anything derived from them is computed after the model answers, memoized (e.g. `get_context_breakdown(agent, itemized=True)` itemizes on read, not in `ContextAttributionHook`). If a change genuinely cannot avoid adding latency there, measure it at realistic scale (dozens of tools, a production-sized system prompt — not a toy fixture), state the number in the PR, and get the developer driving the change to accept it explicitly before merging. A millisecond or two sounds free; the preamble was cut from 455ms to 22–37ms, so each such addition is several percent of that budget, and they compound
- **One session can be served by more than one agent — never cache session state on an agent instance.** The agent cache keys on *configuration* (system prompt, tools, model, skills), so an `@`-mention turn builds a second `Agent`, and each `Agent` builds its own `TurnBasedSessionManager`. Both write the same DynamoDB session row and neither knows the other exists, while `initialize()` never re-runs on a cache hit — so anything a manager loads once and holds goes stale silently. This has bitten twice: conversation history (#741, fixed by aliasing the message list in `_adopt_session_conversation`) and compaction state (#751, fixed by re-reading it every turn in `_adopt_persisted_compaction_state`). Per-session state must be aliased across instances or re-read per turn, and must never move backwards — a clobbered checkpoint or truncation anchor is a prompt-cache **cost** bug before it is a correctness one. **A session id alone does not name a conversation; `(session, user)` does.** Memory scopes history by actor. Anything that finds "this session's" live state in process must match on both (`_conversation_owner_key`), and runtime affinity pins per `(user, session)` (`runtime_session_id_for`) so two users never share a container. When affinity hashed the session id alone and adoption matched on it alone, a second user read the owner's live conversation on dev in 2026-08 (`test_adoption_never_crosses_users_on_one_session_id`, `test_two_users_on_one_session_id_never_share_a_runtime_session`)
- **All dependencies use exact version pins** — no `^`, `~`, or `>=`
- **Never install packages without explicit user approval**

## Feature Flags

**New or in-development features default OFF. A deployment turns them on by choice.** Other organizations build on and deploy this stack, so half-finished work must not switch on for them just because it merged. When a feature is finished, flipping it to default-on (with an `=false` kill switch, like most shipped flags) is its own deliberate change.

**Not everything new needs a flag.** A flag is for two things. The first is **half-finished work** that lands over several PRs. The second is a **capability a deployment may reasonably not want**: one that costs money, adds AWS resources, widens what users can do, or is a product choice.

A finished change that only extends something a deployment already chose does not get its own flag. That means a new optional argument on an existing tool, a mode whose default is today's behaviour, or a new kind of change a tool can now write. Gate it by whatever already gates that tool, and prove it before merge. A flag on such a change protects nothing: old calls behave exactly as before, and the existing switch already turns the tool off. It only postpones the one `toolConfig` rewrite, while doubling the spec, the CDK and workflow wiring, the tests and the docs, and it needs a PR later to retire it.

The proof that replaces it:

- a test pinning the new spec's digest
- `scripts/measure_tool_spec_tokens.py` re-run against dev, with the token growth stated in the PR as one deliberate prefix rewrite at deploy
- for anything that writes a file a user opens, a check in the real app

For example, `redline_word_document`'s whole-paragraph insertions (#1922) shipped with no flag of their own after Word for Mac and LibreOffice both passed the check: Reject All gave back the original, and Accept All renumbered correctly. Word's AppleScript does that check with no clicking: `reject all revisions` / `accept all revisions`, then each paragraph's `list string of list format of text object` and `content of text object`. When in doubt, ask the developer driving the change. Don't add a flag by reflex, or because a brief from another session asked for one.

A feature has up to two switches, one per side, set per environment:

| Side | Where | How it's set |
|---|---|---|
| Backend (authoritative) | `backend/src/apis/shared/feature_flags.py` (`<feature>_enabled()` reads `<FEATURE>_ENABLED`) | CDK `infrastructure/lib/config.ts` → env var on app-api / AgentCore Runtime, from the GitHub environment variable `CDK_<FEATURE>_ENABLED` forwarded in `.github/workflows/platform.yml`. In-development: only `"true"` enables. Unset GitHub variables arrive as `""`, so handle that case |
| Frontend (UI only) | `features` in `frontend/ai.client/src/environments/environment*.ts`, typed by `environments/feature-flags.ts`, read via the `FEATURES` token (`src/app/services/features.ts`) | Compile-time, per build: `environment.ts` = local `ng serve`/tests, `environment.development.ts` = deployed dev (`dev-deploy` configuration), `environment.production.ts` = prod. `scripts/frontend/build.sh` builds `SPA_BUILD_CONFIGURATION`, set by each deploy workflow |

- **The backend is the gate.** The frontend flag only decides what the UI offers (nav items, routes via `canMatch`, buttons), so nothing waits on a request to find out. Never import an environment file from a component; inject `FEATURES`, and provide it in specs.
- **Keep the two in step per environment.** If they drift, the damage is cosmetic: the UI offers a feature whose API 404s, or hides a working one.
- **Adding a flag:** add a field to `FeatureFlags` and all three environment files (in-development: `false` locally and in prod, `true` in dev only if the dev environment has turned the backend on), plus the backend flag, CDK config and test, and the `platform.yml` variable.

### Feature switches stay; rollout switches retire

A default-on flag is one of two kinds, and only one is permanent. The docs-site page (`docs-site/src/content/docs/configuration/feature-flags.md`) records which kind each flag is in its **Kind** column.

| Kind | What it turns off | Lifetime |
|---|---|---|
| **Feature switch** | A capability a deployment may reasonably not want: it costs money, widens what users can do, or is a product choice (`TOOL_SUMMARIES_ENABLED`, `BROWSER_TAKEOVER_ENABLED`, `DICTATION_ENABLED`) | Permanent. It is configuration |
| **Rollout switch** | A change meant to be invisible (a reorder on the turn path, a fix, a cache), kept only so a bad deploy can be undone without a revert (`KB_SEARCH_AHEAD_ENABLED`, `CONFIG_CACHE_ENABLED`) | Retires once the change is proven |

Rollout switches retire because the off path costs something every day it exists. It doubles a code path, often on the turn path, and its tests have to cover both sides. Nobody runs it, so it breaks without anyone noticing. A kill switch that has not been flipped in months gives false confidence.

- **When adding a rollout switch**, write its retirement condition in the reader's docstring and in the docs-site row, and add a line for it to the tracking issue (#1422). The default condition is: shipped in a production release, then at least two weeks there with the switch never flipped and the change's readout recorded. Use a stricter condition when the risk only shows up in a situation prod hasn't reached yet (for example, `AGENT_BUILD_SHARED_SESSION_ENABLED` waits for Runtime V2, because its known risk is a V2 snapshot).
- **Retiring one** is a cleanup PR, batched once per release cycle. Delete the reader, the off path and its tests, any env or CDK wiring, and the docs row. Add a CHANGELOG `Removed` entry naming the variable, because a deployment that set it `=false` loses that opt-out.
- **Promoting an in-development flag to default-on** also means picking its kind. A finished feature usually stays a feature switch. Any rollout switch that guarded its internals can retire on the usual condition. **Turning a flag on in our prod before promoting it is the normal path, and #1798 is the list of flags in that state** with each one's promotion condition: the release gate (`scripts/release/check-new-feature-flags.mjs`) derives the SPA half from `environment.production.ts` vs `environment.ts` and fails a release PR unless the newest release-notes entry says, per flag, "promoted" or why it stays opt-in. A fresh install only gets what defaults on, so a flag that is on for us and off by default is a feature nobody else has. Add a line to #1798 in the PR or release that turns a flag on in prod.

## SSE Event Types

| Event | Purpose |
|-------|---------|
| `message_start` | Start of assistant response |
| `content_block_start/delta/stop` | Streaming content |
| `message_stop` | End of message |
| `tool_use` / `tool_result` | Tool invocation and result |
| `ui_resource` | MCP App UI for a tool (SEP-1865) — payload `{type, toolUseId, resourceUri, html, mimeType, csp, permissions, sandboxOrigin, serverName, icon, toolName}`. Emitted at the tool's `content_block_start` (early frame mount, so the App's bridge is live *while* the model streams the tool's arguments — see `ui_tool_input_partial`); falls back to right after the correlated `tool_result` if the name wasn't known at block start. At `content_block_start` a **header-only shell** (`html: ""`, full `serverName`/`icon`/`resourceUri` but no `resources/read`) is emitted *first* so the App frame's header (icon + server + tool + shimmer) replaces the plain tool rail with no flash; the full html-bearing event follows after the read and, last-write-wins, mounts the iframe (the SPA gates the iframe on a non-empty `html`). Deduped per `toolUseId` (the header shell on its own set, so it never blocks the full emit). HTML fetched server-side via `resources/read` and inlined; `sandboxOrigin` is the proxy.html origin the SPA frames it in (empty unless the mcp-sandbox stack is deployed — inference-api consumes its SSM origin only when `CDK_MCP_SANDBOX_ENABLED=true`; an empty origin means the SPA cannot frame the App). `serverName`/`icon`/`toolName` drive the App frame's connected header (Claude parity): `serverName`/`icon` resolve from the MCP `initialize` `serverInfo` (`title`→`name`, plus its `icons`); `serverName` falls back to the title-cased `ui://` authority, and `icon` falls back to the server's served MCPB `manifest.json` icon — fetched server-side from `<server-origin>/manifest.json` (same-origin only, cached per origin, base64-inlined as a `data:` URI; the runtime MCP protocol carries no icon, so this mirrors what Claude inlines from the installed bundle), else empty (→ generic glyph). A large auto-fetched icon is NOT persisted (size-gated against the 400KB DynamoDB item limit), so it shows live but reloads to the glyph; `toolName` is the agent-facing tool name, carried on the event so the header's name + running shimmer appear atomically with the frame's promotion (not gated on the separately-streamed message content). All three persist with the resource so the header survives reload. Gated by `AGENTCORE_MCP_APPS_HOST_ENABLED` (default true since PR #7; set `=false` to opt an environment out) |
| `ui_tool_input_partial` | Streamed partial tool input for a UI tool (SEP-1865 `ui/notifications/tool-input-partial`) — payload `{type, toolUseId, arguments}`. Emitted repeatedly while the model is still streaming a UI tool's arguments (after the early `ui_resource` mount); `arguments` is the streamed prefix server-side "healed" into a valid object (`apis/shared/mcp_apps/partial_json.py`). The SPA relays each to the App via `ui/notifications/tool-input-partial` so a progressively-rendering App (e.g. Excalidraw's guided camera tour) animates as args arrive; the complete `tool-input` follows once the input is final. Same gating as `ui_resource` |
| `agent_status` | What the agent is doing right now — payload `{type, sessionId, phase, cycle, toolName?, toolUseId?, durationMs?, ok?}`. Emitted from `AgentStatusHook` (`BeforeModelCall` / `Before`+`AfterToolCall`) and drained in `stream_coordinator` exactly like `steering_applied`, before the event it precedes, so "Using list_assignments" reaches the client while that tool is running rather than after its result. Phases: `thinking` (one per event-loop cycle — a three-tool turn reports it four times, and `cycle` distinguishes them), `tool_start`, `tool_end` (carries Strands' own measured `durationMs`, and `ok=false` for BOTH a raised exception and a result with `status: "error"`, except an MCP App form left open for the user: GitHub's write tools return `isError` on purpose there and, on MCP 2026-07-28, mark that result `structuredContent.status = "awaiting_user_submission"` themselves, so the stream, the persisted message and the SPA show "Waiting for you" rather than "Failed"; see `apis/shared/mcp_apps/awaiting_submission.py`). There is deliberately **no "responding" phase** — the SPA already knows text is streaming from the deltas, and a backend-derived duplicate of a fact the client holds first-hand would only disagree at the edges. Durations are live-only and deliberately NOT persisted: a reloaded conversation shows summaries without timings, where a client-invented number would be one the user could not trust. Costs nothing against the model — nothing it produces reaches the prompt, so the cacheable prefix is untouched. Gated by `AGENT_STATUS_ENABLED` (default on with a kill switch); while off the hook is registered but every callback returns immediately and the SPA stays on its cycling phrases |
| `tool_group_summary` | Model-generated one-line summary of a finished tool batch — payload `{type, sessionId, batchId, toolUseIds, summary}`, e.g. "Found the Syllabus Acknowledgment assignment in BIO 101". Produced by a Nova Micro **side-channel** task (`apis/shared/tool_summaries/summarizer.py`) structured exactly like `session_title`: its own Bedrock call on its own messages, concurrent with the agent stream, so it **never appends to the conversation** and adds nothing to the cacheable prefix. Spend is one bounded call per batch (inputs/results truncated at capture in the hook AND again in the summarizer). Lands mid-turn, out of band with the content stream, so it can arrive after the rail that shows it has rendered; the SPA keys it by `toolUseId` (not batch — client-side grouping need not match backend batches, and a group spanning two batches shows the first batch's line). Persisted as `TSUM#` rows in sessions-metadata, reusing the `SessionLookupIndex` GSI — zero new infra — and replayed on `GET /messages` as `toolSummaries`, because the event never re-streams. Deliberately NOT written onto the message content blocks: that is the Converse payload and the cacheable prefix, so a display string there would be paid at model rates every subsequent turn. Gated by `TOOL_SUMMARIES_ENABLED` (default on with a kill switch); while off the SPA's deterministic client-side formatter still renders ("Listed 4 assignments"), so absence is a downgrade in specificity, never a blank |
| `document_extraction` | A named field set was run over one of a call's documents, as typed rows — **one event per document**, all sharing the call's `toolUseId` — payload `{type, sessionId, toolUseId, fieldSet, fieldSetVersion, uploadId, filename, modelId, schemaEnforced, artifactId, downloadUploadId, fields: [{name, title, type, value, state, method, quote, locator?: {kind, value, precision}}]}`. Produced by `document_extract`, which resolves the field set from a skill's reference bundle, makes a **side-channel constrained call** on a dedicated `BedrockModel(strict_tools=True)` carrying the document and the field schema and nothing else — so the typed schema never enters the turn's `toolConfig`, which sits ahead of the system prompt and the whole restored history — and then resolves every value through `source_provenance`, so each row's `state` is one of `supported` / `quote_unsupported` / `unassessed` / `unverified`. **The model is told the values and the states, and nothing more** (~3 tokens of state per field): the values are the answer the user asked for and the follow-up question is the normal case, so withholding them would force a document-sized re-run to answer "what was the budget cap?". The quote, the locator, `precision`, `method`, the rendered table and the `.xlsx` are display metadata and travel here instead, because the content blocks are the Converse payload and the cacheable prefix. Bounded at 200 chars per value and 2,000 per model-facing result, dropping to names and states past that. Drained in `stream_coordinator` on the same pass as `tool_group_summary` and `source_provenance`, via an in-process broker keyed on `(user_id, session_id)` — never the session alone. Persisted as `EXTR#<toolUseId>#<uploadId>` rows in sessions-metadata on the existing `SessionLookupIndex` GSI (zero new infra) and replayed on `GET /messages` as `extractions`, because the event never re-streams — **the upload id is in the key because one call carries N documents** and a key on the tool use alone had them overwrite each other, leaving a reload showing one row set where the user saw fourteen; the row drops its quotes rather than failing the write if it would exceed the 400KB item limit (`quotesOmitted`), since the artifact holds the full table regardless. `schemaEnforced: false` marks a run that fell back to an unenforced request — a grammar-compilation timeout, an unsupported schema feature, or a model that answered without calling the forced tool — so a reviewer can tell types that were guaranteed from types that were merely requested; it is never silent. `modelId` is disclosed because extraction deliberately runs on its own (`DOCUMENT_EXTRACT_MODEL_ID`) rather than the turn's model. Metered, unlike its side-channel neighbours: its input scales with the document, so it writes a `C#` row. Gated by `DOCUMENT_EXTRACT_ENABLED` (in development, off by default) **and** by the turn's skills declaring a field set; while off the tool is never built and nothing is emitted |
| `session_title` | Server-generated conversation title on a session's FIRST turn — payload `{type, sessionId, title}`. Title generation (Nova Micro) runs as an asyncio task concurrent with the agent stream, so the sidebar/top-nav rename while the response is still pending. The finished title is picked up by a non-blocking one-shot check (`_session_title_sse` in `stream_with_quota_warning`) that is polled from two places: the coordinator's live status merge (`poll_side_frame`, every 100ms, so a title that lands during the model's time-to-first-token or a long tool call goes out at once rather than waiting for the agent's next event) and between agent events (its only route while `AGENT_STATUS_LIVE_DRAIN_ENABLED=false`). The task returns the moment Nova answers and persists the title in the background (one keyed `update_item` on the static SK), so the DynamoDB write never sits between generation and the user seeing it. Emitted at most once per stream, possibly after `done` (the SPA parser allowlists it past Completed-state gating); never carries the "New Conversation" placeholder. Best-effort: a stream that finishes before generation emits nothing, and deliberately does not hold the connection open to wait (the SPA clears loading on close, not on `done`) — the SPA's post-close metadata refresh (`refreshTitleFromServer`, up to 5 retries at 400ms) is the fallback, reading the persisted title |
| `quota_session_notice` | **This conversation** has reached the tier's session-notice share of the monthly limit — payload `{type, sessionId, sessionCost, quotaLimit, sessionPercentageOfLimit, thresholdPercentage, message}`. Emitted at the head of the stream right after `quota_warning`, and re-emitted every turn while over the share (dismissal is client-side, same contract as `quota_warning`). `sessionCost` is the session's **lifetime** cost — the `totalCost` aggregate on its metadata row — deliberately not period-scoped: a conversation that opened last month and is spending this month's budget is exactly the one worth surfacing. Share is tier-configurable (`sessionNoticePercentage`, default 25%, 0 disables); the whole runway rides the `QUOTA_RUNWAY_ENABLED` kill switch (default on), which also gates the 50%/75% `quota_warning` rungs. The SPA scopes it to the conversation it names — never shown above another thread's composer |
| `mcp_elicitation_required` | An MCP server is waiting on the user to fill in a form partway through a tool call — payload `{type, interruptId, toolUseId, toolName, serverName, message, fields}`, each field `{name, kind, title, description, required, default, …}` with `kind` one of `text` / `number` / `integer` / `boolean` / `choice` (a choice carries `options: [{value, label}]` and `multiSelect`). Emitted after `message_stop` in the same `done` block as the other interrupts, one per pending form; breadcrumb `PendingInterrupt(kind: "mcp_elicitation")` with the payload JSON-encoded in `elicitation`. Raised by an `ExecuteToolStage` middleware, so the interrupt id is `v1:middleware_execute_tool:{toolUseId}:…`; a call that asks twice pauses twice and the extractor skips the answered round. `serverName` is the catalog's display name, not what the server says about itself. Resume posts `{action: "accept", content}` / `{action: "decline"}` / `{action: "cancel"}` — never null; the content is checked against the server's schema before the replay, and one that does not fit is sent as `cancel`. The schema and message travel on SSE and the breadcrumb only; the answer goes to the server and never enters the conversation. Gated by `MCP_ELICITATION_ENABLED` (in development) **and** the server's `elicitationEnabled`; `docs/specs/mcp-elicitation.md` |
| `source_provenance` | Verdicts for one `verify_sources` call: whether each cited passage is in the document and whether the asserted value actually appears in it — payload `{type, sessionId, toolUseId, claims}`, each claim `{id, state, method, value, quote, locator, uploadId, filename}` (`value` is the asserted value as the model stated it — display metadata like the quote, and what lets a `quote_unsupported` name the number it cannot confirm instead of making the reader guess). `state` is one of `supported` (the only state that earns a plain page badge), `quote_unsupported` (the passage is real, the value is not in it — the hallucination signal, and it must render like one), `unassessed` (located but the value is not the kind of thing findable in it) or `unverified` (no passage located). `locator` is `{kind, value, precision}`: `kind` is the unit the document actually has (`page`/`paragraph`/`line`, so a .docx never claims a page) and `precision` is **always present** — an optional flag whose absence reads as exact is how a guess gets rendered as `p. 234`, so an `estimated` position is hedged `p. ~12`. Derived in exactly one place (`apis/shared/files/source_provenance.py`, pure stdlib); there is deliberately **no** public function taking the two underlying booleans, because a caller could pass a pair it invented and re-certify the weaker claim. The model's own tool result carries the `state` per claim and **nothing else** (~3 tokens each, so it can correct a `quote_unsupported`); the quote, locator and method travel on this event and a `SRCV#` row in sessions-metadata (the `TSUM#` pattern, zero new infra), never on the message content blocks, because those are the Converse payload and the cacheable prefix. Drained in `stream_coordinator` beside `tool_group_summary` and flushed once before `done`; replayed on `GET /messages` as `sourceProvenance`. The SPA renders it under the answer (never inside the collapsed tool rail): a clean run is one quiet line, and anything `quote_unsupported` opens itself, because a warning behind a click is not a warning. Runs only when the model calls the tool, after it has read a document — never in a `Before*` hook. Gated by `SOURCE_PROVENANCE_ENABLED` (in development: only `"true"` enables; `docs/specs/source-provenance-verification.md`) |

Every other shared agent keeps block-with-message (D5, `stream_error`). Emitted before `message_start`, beside `quota_session_notice`. **SSE only, never the prompt** — the model is not told what was dropped, so the cacheable prefix is unaffected — and not persisted, because the next turn re-derives it. The SPA ignores it until the Projects UI (PR-1.8) renders it |
| `model_retry` | Backend is retrying a failed model call instead of surfacing it — payload `{type, attempt, delaySeconds}`. Emitted from Strands' `EventLoopThrottleEvent`; `attempt` is 1-based and counted per turn in `stream_processor` (the raw event carries only the delay). **Timing caveat:** Strands sleeps the backoff *inside* its hook and yields the event afterwards, so it lands as the next attempt BEGINS, not when the wait starts — `delaySeconds` describes the gap just endured, it is not a countdown. It also cannot cover the failing model call itself, which is indistinguishable from a slow healthy one. The SPA swaps the loading indicator's cycling phrases for a fixed amber notice, cleared on `message_start`/`done` |
| `steering_applied` | A follow-up the user typed **while the turn was still streaming** was injected into that running turn at a tool boundary — payload `{type, sessionId, entryId, text}`. PR #916 queues a mid-stream Enter in the composer and flushes it on the turn's falling edge; mid-turn steering lands it at the next tool boundary instead, appended as a `{"text": ...}` block on the same user-role message that carries the tool results, so the agent reads it before choosing its next action. Emitted after that batch's `tool_result` events (so the thread renders in the order the model will see) and never after `done`. The transport in is the session's single-flight **lease row** — `steerQueue` + `steerFor`, owner-scoped exactly like `cancelRequestedFor`, armed by app-api's `POST /sessions/{id}/steer` and deleted with the lease at turn end. Consumption is **commit-on-append**: the hook peeks at `AfterToolsEvent` and clears the inbox entry only on the `MessageAddedEvent` for that same message, because `AfterToolsEvent` fires from a `finally` and so also fires on the interrupt path, where the mutated message is discarded — a hook that consumed on read would destroy the user's words whenever a steer landed on the same tool batch as an OAuth consent. Absence of this event is the fallback, not an error: a turn that calls no tools has no boundary to inject at, and a steer can lose the race with the turn's end — in both cases the entry stays queued and #916's end-of-turn flush sends it as a normal turn. Append-only against the cached prefix (the injection lands inside the segment the `strategy="auto"` message-level cachePoint covers), so it never rewrites the prefix. Gated by `MID_TURN_STEERING_ENABLED` (default on with a kill switch); while off the steer endpoint 404s and the hook returns immediately. See `docs/specs/mid-turn-steering.md` |
| `handoff_brief_fallback` | A `handoff_brief` invocation's answer when no brief was written — payload `{type, handoffId, reason}`, `reason` one of `flag_off`, `not_open`, `busy`, `preempted`, `quota`, `refused`, `timeout`, `error`, `tool_use_only`, `short_source`, `history_ends_on_user`. Streamed only on a brief's own stream (never a turn's), followed by `done`; the SPA keeps the excerpt in the card and discards any brief text already streamed. A written brief streams as `content_block_delta` frames and ends with `done` carrying `briefHash` and `cacheStatus`. Gated by `HANDOFF_BRIEF_ENABLED` (in development) |
| `stream_error` | Conversational error |
| `oauth_required` | External MCP tool needs user consent — payload `{providerId, authorizationUrl, interruptId?}`, one event per provider emitted after `message_stop`. Two flavors. **Interrupt-driven** (`interruptId` present): `OAuthConsentHook` paused a tool call mid-turn; the SPA resumes that exact turn by POSTing the id back. **Pre-flight** (`interruptId` *absent*): the tool never registered because the MCP server refused the pre-flight `tools/list` — since the consent hook is `BeforeToolCall`, it can't fire for an unregistered tool, so without this event the tool vanishes with no explanation. Nothing is paused, so the SPA shows the Connect affordance and must NOT resume; a synthetic id would be worse than none, because the resume guard in `inference_api/chat/routes.py` refuses unknown ids (`ResumeUnavailable`, streamed as "send your message again") and the user would be told to start over right after consenting. Pre-flight events are re-emitted every turn until consent lands: a rebuild fails the pre-flight again, and a cache hit on an agent built without the tool asks the vault (`recheck_consent`, ~200ms, paid only by such agents), rebuilding once a token is there. The build also names the dropped servers in a system-prompt note so the model does not invent their tools and are deliberately not persisted as `pending_interrupt` breadcrumbs — those are keyed by interrupt id for the resume path. The SPA dedupes by `providerId` and suppresses a dismissed pre-flight prompt for the tab session. Before emitting, the runtime asks the AgentCore vault directly: a vaulted token is warmed into `oauth_token_cache` and the pre-flight retried, so a user who already consented gets the tool back instead of losing it for the life of the process |
| `user_question_required` | The agent paused to ask the user structured clarifying questions — payload `{type, interruptId, toolUseId, questions}`, where each question is `{header, question, multiSelect, options: [{label, description?}]}`. Emitted after `message_stop` in the same `done` block as `oauth_required` / `tool_approval_required`, one event per pending prompt. Unlike those two the interrupt is raised by the **tool itself** (`ask_user_question`, via `ToolContext`) rather than by a `BeforeToolCall` hook; Strands routes both through `_stop_for_interrupts`, so the `PausedTurnSnapshot`, the resume route and the `PendingInterrupt` breadcrumb (`kind: "user_question"`, questions JSON-encoded) need no special case. The SPA renders a picker and resumes the same turn by POSTing an `interrupt_responses` entry whose `response` is `{answers: {"<header>": {selected, text}}}` — always an object, **never null**: `ToolContext.interrupt` only treats a non-None response as an answer, so a null would re-raise the interrupt forever ("Skip" sends `{skipped: true}`). The picker always offers Other + Skip, so the model must not include them as options. Cost: the tool spec is a constant in the cacheable `toolConfig` prefix and the questions travel on the SSE channel only — just the one-line formatted answer block re-enters the conversation. Gated by `ASK_USER_QUESTION_ENABLED` (default on with a kill switch); while off the tool is never registered, so the model falls back to asking in prose |
| `browser_login_required` | The agent paused so the **user** can sign in to a site it cannot reach — payload `{type, interruptId, toolUseId, sessionId, browserSessionId, browserId, viewport, deadlineAt?, targetUrl?, reason?}`. Emitted after `message_stop` in the same `done` block as `oauth_required` / `user_question_required`, one per pending handover. Raised by the tool itself (`request_user_login`, via `ToolContext`) like `ask_user_question`, so the `PausedTurnSnapshot`, the resume route and the `PendingInterrupt` breadcrumb (`kind: "browser_login"`) need no special case. `sessionId` is the **conversation** id as everywhere else; the browser is `browserSessionId` — app-api's live-view route is owner-scoped by conversation and resolves the browser server-side. **There is deliberately no URL on this event.** `generate_live_view_url` signs with SigV4 *query* auth and caps at 300s, so a minted URL is dead before a human reacts and dead again on reload; app-api mints one per request instead (`assert_no_url` enforces this on the interrupt, the event and the persisted row, rather than trusting it). `viewport` rides the event because DCV's `remoteWidth`/`remoteHeight` must match the session viewport or the stream crops — a second copy of `1280x800` in the SPA is a copy that will drift. Resume posts `{completed: true}` / `{skipped: true}` — always an object, **never null**, or the interrupt re-raises forever. While the user holds the browser the automation stream is `DISABLED` at the service, so the agent provably cannot act; the idle reaper exempts the session until `deadlineAt` and no further, which is what stops a walked-away-from takeover billing to its TTL. Cost: the tool spec is a constant in `toolConfig` for granted users (~200 tokens) and the whole round trip adds one short line to the conversation — the live view is a stream the model never sees. The SPA never declares client tools, so a web turn never sees this; the terminal client does (shell commands, file reads/writes on the user's machine, each approved by the user before it runs). Resume posts `{output, isError}` or `{declined: true}` — never null. Specs, schemas and results are bounded because all of them are prompt text. See `docs/specs/TUI_WEB_PARITY_SPEC.md` § Client-executed tools |

Today A2A is **client-only** — `A2AAgentConfig` (`apis/shared/tools/models.py`) describes remote agents we call out to; we do not yet expose an A2A server / `AgentCard`. **When the first A2A server construct lands** (Strands `agent.to_a2a()`, an `A2AServer`, or a hand-built `AgentCard`), its advertised `capabilities` MUST include `streaming=True`. Without it the A2A SDK client silently falls back to non-streaming, never receives a `completed` event, and hangs until its ~40-minute timeout (ref-repo `aws-samples/sample-strands-agent-with-agentcore` commit `50c9112`).

## Cross-Package Contracts

- Backend route handlers define the API shape; frontend TypeScript interfaces must match
- Breaking changes to an endpoint require updating both packages in the same PR
- SSE event types are part of the contract — changes must be coordinated. **Two clients consume it:** the Angular SPA and the terminal client in `tui/` (`aps_tui/client/agent_events.py` is its parser). A new event is harmless to the TUI (it logs unknown names once per turn) but a renamed or reshaped one breaks it, so check both when changing the table
- Two request fields exist only for the terminal client and must stay optional with web-identical defaults: `client_surface` (prompt guidance for the surface; `"web"`/absent is byte-for-byte the default prompt) and `client_tools` (tools the *client* executes via the `client_tool_call` interrupt; `apis.shared.client_tools`). `docs/specs/TUI_WEB_PARITY_SPEC.md` is the contract for both
- `app_api`, `inference_api`, and `agents/` are independent consumers of `apis.shared`. They must never import from each other — only from `apis.shared`. If something is needed by more than one of them, move it to `apis.shared`. This is enforced by `tests/architecture/test_import_boundaries.py`.

### Inference API boundary

The `inference-api` runs inside an AgentCore Runtime container. The runtime data plane (`https://bedrock-agentcore.<region>.amazonaws.com/runtimes/<arn>/...`) only proxies the standard AgentCore paths — `POST /invocations` and `GET /ping`. **Other HTTP paths return 404 from AWS before the request ever reaches the container**, so any custom route added to inference-api is unreachable in cloud. Local dev is misleading because `localhost:8001` bypasses the runtime gateway entirely.

**Rule:** Don't add routes to `inference-api` unless they're part of the AgentCore Runtime invocation path (i.e. the chat router that owns `/invocations` and `/ping`). User-facing CRUD-ish endpoints — even ones that share dependencies with the agent loop — belong in `app-api`. If a coding agent suggests adding endpoints to inference-api "because it has the workload context," push back: the right pattern is to mint workload context on app-api via the `AGENTCORE_RUNTIME_WORKLOAD_NAME` mint fallback in `apis/shared/oauth/agentcore_identity.py`.

If you're tempted to add to inference-api because of an existing route there (`converse_router`, `voice_router`), don't use them as templates without confirming their access path — they predate this rule and may rely on bypasses (API key, WebSocket upgrade, direct container reach in environments where the runtime isn't the only path).

### RBAC: the AppRole record is the source of truth

A role grants a tool/model/skill by listing it in its own `grantedTools` / `grantedModels` / `grantedSkills` (or by granting the `*` wildcard, or inheriting from a parent). **That is the only thing access checks read.** The `allowedAppRoles` field on a resource (tool, model, skill) is a *derived, display-only* projection of those role records — never an independent grant.

**Rule:** When an admin page offers a "which roles can use this?" picker on the resource, it must write *through* to each role's `granted*` list (`set_roles_for_tool`, `set_roles_for_model`) and derive the field back on read (`hydrate_model_roles`). Never persist a role list on the resource and expect it to grant anything: it will silently do nothing, and the resource page and the role page will disagree.

Every model-access decision reads one predicate: `grants_model_access` in `apis/shared/rbac/model_access.py`. It refuses a catalog row with `enabled: false` (wildcard holders included), then allows a role grant (`grantedModels` or `*`), then the legacy JWT-role list on the row (`availableToRoles`). A model id with no catalog row is **refused**, wildcard holders included, because pricing lives on the row: it would run unmetered and free against quota (a prod Agent Designer preview on `global.*` Haiku 4.5, which prod catalogs only as `us.*`, did exactly that in 2026-11). A catalog that can't be read fails open to the role grants instead; callers holding a `record` from `resolve_effective_model` pass its `catalog_read` so a `None` from an outage is not mistaken for "no row". **The rule spans services, not just one class:** `AppRoleService.can_access_model` / `filter_accessible_models` (chat turn, api-converse, an Agent's model override, `account_tools`) and `ModelAccessService` (the `/models` catalog, Agent Designer validation) all delegate to it. It lives in `apis.shared` because those callers sit on both sides of the import boundary. Never write a second model-access check, and never mirror one in `agents/`. Call the shared one. It has diverged twice. First it split *within* `ModelAccessService` (one method gated on `allowed_app_roles`). Then it split *between* services (#798): the chat path ignored `enabled` and `availableToRoles`, so a legacy-granted model was listed and then refused, and a disabled model was hidden yet still ran.

Callers resolve retirement first (`resolve_effective_model`) and check the **effective** id. They pass `record=effective.record`, so the turn path judges the row it already resolved and reads the catalog once. Without `record`, `can_access_model` finds the row in the cached catalog itself.

### Auth dependency on app_api routes

The SPA sends an httpOnly session cookie — not `Authorization: Bearer`. A route that declares a bare Bearer-only dependency on the SPA-facing surface causes a 401 → centralized redirect loop the moment the SPA hits it.

**Rule:** New routes under `apis/app_api/` use `Depends(get_current_user_from_session)` from `apis.shared.auth.dependencies` for user authentication. Admin routes use `Depends(require_admin)` (which chains through the same cookie dependency). The only exceptions are the API-key feature (`auth/api_keys/`, uses `X-API-Key`) and voice mode (`voice/`, uses a voice-ticket cookie) — both handle auth on their own terms and should not be used as templates for ordinary user routes.

Do not reintroduce a Bearer-only `Depends(...)` on any user-facing route. If you find one in older code, migrate it to `get_current_user_from_session`.

**The same session, presented two ways.** `SessionRefreshMiddleware` resolves a BFF session from the httpOnly cookie *or* from `Authorization: BFF <sealed>` (the terminal client, which has no cookie jar). Both land in `request.state.bff_session`, so `get_current_user_from_session` and every route behind it work unchanged for either client — a new route needs nothing extra to be reachable from the terminal. Header-presented sessions are exempt from `CSRFMiddleware` (a browser cannot attach `Authorization` cross-site on its own), and sessions for the terminal are minted by the device-authorization flow under `/auth/cli/*` (`docs/specs/CLI_DEVICE_AUTH_SPEC.md`), which reuses `/auth/callback`. Do not add a third way to present a session; extend `SessionRefreshMiddleware` if a new client shape ever needs one.

### App shell chrome: `data.chrome` on the route

The app shell (`app.ts` / `app.html`) decides what surrounds a page by reading `data.chrome` off the active route, never by testing the URL. Three states:

| `chrome` | Sidenav | Content box |
|----------|---------|-------------|
| *(unset)* | chat nav | `mx-auto max-w-7xl` |
| `'minimal'` | none | none — page fills the shell (the artifact viewers, `artifacts/:id` and `shared-artifact/:shareId`) |
| `'admin'` | **admin nav** (`AdminNav` replaces the sidenav's body) | none — `AdminLayout` owns its own padding |

**The walk is deepest-*declared*-wins, not leaf-only** (`shared/utils/route-chrome.ts`). `'admin'` is declared once on the parent `/admin` route and every child declares nothing; with the default `paramsInheritanceStrategy` (`'emptyOnly'`) Angular does **not** copy `data` onto a child that has its own path and component, which every admin page has. A leaf-only read therefore sees nothing on any of them. A leaf can still opt out by declaring something else (`'full'`).

**Rule:** The admin console's navigation is the *sidenav's body*, not a column inside the page. Never re-add an `<aside>` nav to an admin page — the point of the swap is that admin surfaces (cost tables, the model catalog, the role matrix) get the full content width instead of sitting between two navigations, one of which lists conversations that cannot be opened from `/admin`.

Three things that look optional and are not:

- **`Sidenav.isAdminChrome` and `App.adminChrome` both read the flag.** Do not substitute a `/admin` URL test in either: two independent answers to "are we in the console?" is one more than can stay in agreement.
- **`AdminLayout` carries its own small-screen nav opener.** The shell's floating hamburger is gated on `HeaderService.showContent()`, state the *session page* owns and admin pages never set — relying on it would make the admin nav reachable or not depending on where the user had been first.
- **`.sidenav-body-enter` is global in `styles.css` on purpose.** The chat nav and the admin nav swap into the same slot and must arrive identically. Angular scopes keyframe *names* per component, so a copy of the rule inside a component compiles to a separately-named animation that looks identical today and drifts the first time one is tuned. Add a section to the stagger by applying the class plus an `animation-delay`, not by writing new keyframes.

## Debugging Quick Reference

- **Tool not appearing:** Check `__init__.py` export, RBAC permissions, `enabled_tools`, ToolRegistry
- **Session not persisting:** Check AgentCore Memory config, session_id, TurnBasedSessionManager flush
- **SSE stream disconnecting:** Check 600s timeout, client connection, quota exceeded events
- **Usage at $0 / not counted against quota:** the call's model id has no catalog row, so it priced to `None`. Note what `UnmeteredModelCall` cannot catch: it fires only when a call with usage prices to nothing, so a row priced on the *wrong basis* — the interrupted-turn bug, where a cache write was billed as plain input — looks metered and stays silent. The `UnmeteredModelCall` EMF metric (PromptCache namespace, alarm threshold 0) fires per such call; the dashboard's "Unmetered calls by model" widget names the id. A turn, Agent binding or api-converse call that *names* an id with no row is now refused by `grants_model_access`, so the alarm firing means a path that skips that check (the hard-coded `Defaults.MODEL_ID`, voice, `DOCUMENT_EXTRACT_MODEL_ID`). A turn that names no model runs on the user's saved default, then the catalog's `isDefault` row (`_resolve_fallback_model`); the hard-coded `Defaults.MODEL_ID` is reached only when the catalog has no enabled default, and prod has no row for it. **Voice** prices only when the catalog has a row for `amazon.nova-2-sonic-v1:0` (curated as "Nova 2 Sonic" on the Bedrock tab): its `input`/`output` are the TEXT rates and `speechInput`/`speechOutputPricePerMillionTokens` the speech ones, billed per bucket by `CostCalculator.calculate_voice_cost`. The row's SPEECH output modality keeps it out of the chat picker
- **Cost spike / cache miss:** Check `cacheStatus` + `toolConfigHash`/`systemPromptHash`/`historyHash` on the session's `C#` rows in sessions-metadata (or `GET /admin/costs/sessions/{id}/calls`) — the hash that changed between consecutive calls names the cache-buster. Rule out the explained case first: `agentSwitched` on the row means an `@`-mention ran that turn on a different Agent, which re-writes the prefix on purpose and looks identical to the regression (`agentSwitchMissCount`/`agentSwitchUsd` are a subset of the totals — subtract for unexplained waste). Likewise `modelSwitched`: a mid-conversation model switch continues the conversation in place, and each model has its own cache, so the first call on the new model re-writes everything with *unchanged* hashes (`modelSwitchMissCount`/`modelSwitchUsd`, EMF `ModelSwitchMiss`; disjoint from the agent-switch pair, so subtract both). **A `hit` is not proof the prefix was cached** — `partial_miss` marks the calls that read a leading segment (tools+system) while re-writing the history behind it, which costs like a full miss; its tell is a flat `cacheReadInputTokens` next to a `cacheWriteInputTokens` that tracks the whole conversation, and its dollars are in `wastedUsd` with `partialMissCount`/`partialMissUsd` naming the subset. Rows written before that status shipped still say `hit` — nothing is backfilled. **A `cacheStatus` of `estimated` is not a verdict and never a lead**: that call never reported usage (a turn the user stopped, cut mid-generation), so its tokens are an attribution rather than a measurement and its `wastedUsd` is zero by construction — the row's `usageEstimated` map names what produced each figure (`agents/main_agent/streaming/interrupted_usage.py`)

## Coding Standards
