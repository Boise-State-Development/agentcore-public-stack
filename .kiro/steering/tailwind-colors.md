# Color Usage Reference

**Never use Tailwind's built-in color palettes in application code.** No `bg-blue-600`, `text-red-500`, `border-amber-300`, `ring-emerald-400`. Grays and other neutrals (`gray`, `slate`, `zinc`, `neutral`, `stone`, plus `white` / `black`) are fine — they are not part of the themed surface.

Every color belongs to one of three groups. Identify the group, then pick the utility.

| Group | Meaning | Utilities | Defined in |
| --- | --- | --- | --- |
| Brand | Accent and interactive: buttons, links, selected states, focus rings, active tabs | `primary-*`, `secondary-*`, `tertiary-*` | `src/styles/generated/brand-theme.css` (generated) |
| Status | Fixed meaning: error, warning, success, informational | `state-danger-*`, `state-warning-*`, `state-success-*`, `state-info-*` | `src/styles/tokens/state.css` |
| Category | Fixed identity: which vendor, which file type | `vendor-*`, `filetype-*` | `src/styles/tokens/identity.css` |

Only the brand group follows `src/branding/brand.config.ts`. Status and category colors are deliberately fixed — a red error banner stays red for an organization whose brand color is red, and a spreadsheet badge stays green.

Full rebranding documentation lives in `frontend/ai.client/src/branding/README.md`.

## Brand utilities

```html
<!-- Solid fill with white text -->
<button class="bg-primary-accessible text-white transition-[filter] hover:brightness-95">

<!-- Colored text or icon, light surface then dark -->
<span class="text-primary-accessible dark:text-primary-accessible-dark">

<!-- Decorative tint -->
<span class="bg-primary-50 dark:bg-primary-900/30">

<!-- Focus ring -->
<button class="focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-primary-accessible">
```

### Why `accessible` instead of a numbered step

A numbered step is not safe for an arbitrary configured brand color. A bright color at step 500 or 600 can leave white label text well below 4.5:1. The build derives `{role}-accessible` and `{role}-accessible-dark` by adjusting lightness only — hue and chroma are preserved — until the color clears AA, and leaves it untouched when it already passes.

Use them wherever legibility depends on the color:

- Solid fills carrying white text
- Brand-colored text or icons

Numbered steps remain correct for decorative tints, where nothing has to stay readable against the color. If text sits on a tint, verify it.

### Two rules that look wrong but are not

**Solid fills take no `dark:` override.** The contrast that matters is fill against its white text, which is identical in both themes. Lightening the fill in dark mode only erodes it. Write `bg-primary-accessible` alone.

**Hover uses `brightness-95`, not a darker step.** For a light configured brand color, the accessible variant can already be darker than step 700, so `hover:bg-primary-700` would *brighten* the button and drop it below AA. A brightness filter moves in the right direction for any configured color.

## Status utilities

```html
<!-- Error alert -->
<div role="alert" class="border border-state-danger-200 bg-state-danger-50 text-state-danger-800
                         dark:border-state-danger-800 dark:bg-state-danger-900/20 dark:text-state-danger-300">

<!-- Invalid input -->
<input aria-invalid="true" class="border-state-danger-500 focus:ring-state-danger-500" />
<p role="alert" class="text-state-danger-600 dark:text-state-danger-400">...</p>
```

Blue is ambiguous in older code, serving as both the original accent color and the informational color. When replacing a `blue-*` utility, decide which it is: interactive elements become `primary-*`, informational notices become `state-info-*`. Do not bulk-replace.

## Adding a token

Status colors go in `state.css`, category colors in `identity.css`.

- Copy the value verbatim from `node_modules/tailwindcss/theme.css` so the change is invisible.
- Keep it in `oklch()`. Converting to hex clamps to sRGB and shifts the color on wide-gamut displays.
- Use a literal value, not `var(--color-red-600)`. Tailwind drops unused theme variables from the build, so the reference can resolve to nothing.
- Define only the steps you need.

Chart series colors are the one exception and belong in a TypeScript constants module, not CSS, because Chart.js needs a resolved color string rather than a utility class.

## Never edit the generated file

`src/styles/generated/brand-theme.css` is machine-written from `brand.config.ts` by `scripts/branding/generate-brand-theme.ts`, and is regenerated by the `prebuild` / `prestart` npm scripts. Hand edits are overwritten. To change a brand color, edit `brand.config.ts`.

Note that invoking `ng serve` or `ng build` directly bypasses npm lifecycle hooks and therefore skips the generator, leaving stale colors. `start.ps1` runs it explicitly for this reason.
